# Journey System (Max Strength App) — read this first

Journey is the coaching app for **Max Strength Fitness** studios: trainers record workouts, machine settings and notes on iPads on the gym floor; studio leaders run the studio from the same app. It replaces the Claris FileMaker system the studios use today and syncs people, bookings and contracts from **Mindbody**.

How the business works (packages, renewals, roles, where data lives) is in **`docs/business/`**. Read the relevant page before building anything that touches clients' packages, renewals or permissions.

**`docs/START-HERE.md`** is the orientation page — the three systems and who owns what, the map of the folders, the project's invented vocabulary, how a change reaches an iPad, and the rules that must never break. It is written for AJ (who does not write code), so it is also the fastest way for a new session to get the shape of the project before diving into this file's detail.

**What a session is** — twenty minutes, one set to failure on five to eight machines, an iPad in the non-dominant hand that is set down at every machine and looked at twice per machine. The trainer's clicker counts reps; the app is a guide for set-up and a log for outcomes, never a coach, and never suggests a progression. Read **`docs/business/the-floor.md`** before touching the Active Session, the Now Bar, the briefing or the post-session screen. It opens with **Ken Hutchins' definition of exercise**, which is the source every rule below is downstream of — if a change is not within that definition, it is not within the method, and naming the clause it breaks is the fastest way to say why.

**Journey is not a fresh start.** The studios are mid-migration off FileMaker, and a roster during that period is a mix of brand-new clients and clients with several hundred sessions behind them. A client's history did not begin when Journey first saw them: an empty Journey history means "no detail here", never "this never happened". Read **`docs/business/migration-and-prior-history.md`** before building anything that counts, dates, averages or trends a client's history.

## Decisions already made — don't change them without asking

**Product**
- iPad-first, portrait and landscape. Nothing tappable under 40px; hover is never the only way to find something; names are never truncated.
- **Corporate owns the method, so corporate reads it before adopting it** (the catalog gate, Sep 20). A studio's own machine carries a whole definition, method included; publishing one makes those words Max Strength's on every floor. An admin reads the machine in the catalog editor and may rewrite it first, and what they saved is what publishes. Publishing is refused while the machine is missing anything the app would render wrong or the floor would coach wrong — the one place this app holds a write, and it is the opposite case from "never block a save", which protects a trainer mid-session.
- **Sentences, not scores.** Every claim a screen makes has a named minimum sample, and below it the screen says "not enough data yet".
- A confident wrong number is worse than a missing one (the "In Journey since" rule).
- **Every number has a reader.** A field we write must be read by at least one screen, report or job; a write with no reader is a bug to fix, not a field to delete (`docs/business/data-and-metrics.md`). The session's `clientAge` / `clientOccupation` / `clientIsRetired` / `clientActivityLevel` / `clientClinicalProfile` snapshot is deliberate — it is the substrate for cohort analytics (starting weights, which machines suit whom, pace, the studio's own claims) and it is a SNAPSHOT because those facts change. Any cohort metric keeps the existing rules: a named minimum sample, cells k-anonymous at five (`CELL_MIN_CLIENTS`), no clinical data in anything a signed-in trainer can read per-person, and recognition never ranking.
- **Prior history is real history.** `client.priorHistory` records what a client did before the cutover (`src/lib/prior-history.ts`); `total = journey count + (sessions - importedCount)`. The reconciler owns what Journey can see, the prior record owns what it cannot, and they never write the same field. Any importer of historical sessions MUST raise `importedCount`. Never call a client new, draw a trend as their whole story, or say "never tried" off a low Journey count during migration. **Every sentence a screen says about a client's past** ("first time", "#N", a break, "All time", "Client since") comes from `src/lib/history-claims.ts`, with coverage judged by the client's HOME studio's cutover (Sep 24 2026).
- **Nothing contacts clients or trainers** — no email, SMS or push outreach. In-app only.
- Use the design tokens (`equipment.tokens.css`, and `admin.tokens.css` in admin screens); no raw hex. The red kaizen mark is reserved for rep quality.
- Dates are the studio's Eastern day (`src/lib/studio-time.ts`).
- Admin / Operations screens follow `src/features/admin/README.md` (dirty-tracked saves, only the diff is written, plain studio English).
- **Anything a trainer RATES about a client is the Dial; anything they WRITE carries a Loudness** (reporting round, Sep 16). No screen builds another rating control or another priority vocabulary. The living assessment is **Pulse** on every label (code and Firestore still say check-in / subjective).
- **A note is a thread, not a fact** (Notes round, Sep 20). Something opens, runs a while, and then closes or deepens; updates hang off the original rather than becoming new notes, so the whole story is in one place. The window, the loudness and `resolvedAt` live on the ROOT and nowhere else. **Contradicting a note ADDS to it** — a client who does the movement fine gets "performed overhead, seemed okay" on the thread, because the good outcome may have happened *because* of the note, and closing would delete the reason it went well. Any trainer may close a thread and any trainer may reopen it. **The three zones are derived, never set**: Open (a live or coming window, or an "always" note that shouts), Standing context (an "always" note at plain loudness), Resolved. One vocabulary, not two that drift. **Dismissal is per trainer, private, and undone by any update** — that is what keeps a quieter briefing from becoming a briefing that withholds, and nothing is ever hidden without a way back to it.
- The bottom-bar tab is **My Studio** (My Studio round, Sep 18–19): Relay · Machines · Team · Studio. **My Studio is where you run the studio; Operations is where you look at it** (AJ, Sep 18) — a studio's own settings live there once, and nothing on Operations is a second editor of them. Sharpened by AJ Sep 21, and the better test for which one a change belongs in: **My Studio answers "how can I help the team right now?"** (what is going on today, what everyone is doing, what is coming up, our machines — present tense, participatory, somewhere a trainer GOES when they have a gap); **Operations answers "where are we going wrong, and where are we going right?"** (locate the problems, catch what is catchable, find the small opportunities worth turning into big rewards — investigative, somewhere a leader OPENS to find what they would otherwise miss). The one deliberate exception (AJ, Sep 19): Operations → Floor mounts the SAME floor editor as My Studio → Machines — one implementation, two doors, never a second editor.
- **Operations is split in two (Operations overhaul, Sep 19).** Operations is the studio-management area, always one studio, nine tabs, opened daily by studio leaders, head trainers, studio owners and trainers with the grant; the **Admins dashboard** takes everything corporate-only (the standard template, the master catalog, every location, Limbo, system tools, bug reports, the company's data) and is reached by administrators and the founder only. The first screen of Operations is the **Overview** — "not the Monday page: studio management opens this every day" — a summary layer where every panel drills into its own tab; Insights and Machine fit are deliberately not on it. **Nothing on the Overview is a score:** a sentence with its proof, an action (Acknowledge, Snooze, Dismiss, Got it) and a door. Changes are held against the day the session was for; a cancellation with another booking that week reads as a reschedule. Every note has a mattering window (Always · From – until · Only on a day) and comes up for review after 60 days rather than dropping. The To-Do screen is **Relay**, its first section (Relay round, Sep 16; it was the Planner from the rework earlier that day): Floor · Mine · Notes · Network (franchise and super roles); the old Team tab is My Studio → Team; its view id is still `studio-tasks`; the folder is `src/features/relay/` (renamed from `features/planner/` in the beta-prep trim, Sep 17), with the Floor tab and the task data layer in `src/features/studio-tasks/`. AJ's brief suggested "Studio Command Center" and asked for something less corporate — Relay was the pick. **Nothing pings anyone**: the Pulse, kudos and hand-offs are in-app, and a bell rings only for what a person opted into. Notes are private to their author; **Share** copies a one-client note onto that client's record, **Share with colleagues** copies it to `studios/{s}/noteShares`, and **All MSF studios** copies it to every studio's `noteShares` as a team share — sharing is always a copy, never a visibility flag, and every save republishes.
- **Recognition, never ranking, inside a studio** (Relay): kudos are shown per person to leaders and to the person; no points, badges, per-person streaks or leaderboards among trainers. Studios may be ranked on the Network tab.
- **Max Strength owns the method; a studio owns its hardware** (machine authoring, Sep 20). The company franchised out of three corporate locations, so the METHOD is the product — musculature, movement pattern, kinematics, cadence, both turnarounds, the handoff, the key cues — and every location reads the same words. What a location genuinely owns is the UNIT in its building: the name it uses, the baseline positions, the body-type adjustments, the dials and their defaults, the starting load, a photo. Safety is additive: a studio may ADD a warning, contraindication, sequencing note or alignment checkpoint, never remove one of the catalog's. `src/lib/machine-template.ts` is the one answer, method is the REMAINDER so a new field defaults to corporate, and `scopeOverrides()` strips the rest at the write. An ADMIN is not bound — that is what makes it safe to enforce on a studio. A studio's override is a DIFF: a field it never touched keeps live-inheriting corrections.
- Sharing between studios is the studio's choice, per machine and per tip or note (a "Share with all MSF studios" switch). Comments stay within the studio; a tag rings the tagged person's bell and nothing else.

**Data**
- Mindbody owns people, bookings and contracts; Journey owns coaching data. A Mindbody client lives at `clients/{mindbodyClientId}` — no name matching, ever. **Except the second person on a shared number** (client-identity round, Sep 23 2026): both Mindbody sites number clients from 100000001, so when the plain number already belongs to someone on the OTHER site, this person lives at `clients/{siteId}-{mindbodyClientId}`. `src/lib/mindbody-site.ts` is the one rule (the webhook carries a copy); a record's Mindbody id is always the `mindbodyClientId` field, never parsed from the doc id.
- Every query names the studios it reads (`src/lib/tenancy.ts`). Sessions are scoped by **client**, not studio.
- Never write to a collection from inside a listener on that same collection. A failed read means "unknown", never "empty". No per-client queries in a loop.
- Keep running totals (`trainerTally`, `machineStats`, trainer rollups) instead of re-reading history when a screen opens.
- **A booking is done when Journey logged a session for that client that day** (AJ, Sep 24 2026). Bookings never come back Completed or No-Show — the sync and the webhook write Scheduled or Cancelled, and Mindbody's own marking stays manual — so read what happened to one through `src/lib/booking-state.ts`, never from `status` alone. `docs/rounds/2026-09-24-done-means-logged.md` is the round.
- Firestore rules apply to whole documents: anything some roles must not see goes in its own document.
- **Don't change the Mindbody integration, Cloud Functions or the Firestore structure without an explicit OK.**

**How we work**

- Explain changes in plain language as you go, and give click-by-click Windows / PowerShell steps for anything that has to be run on the PC.

## Roles

`ROLE_LABELS` in `src/types.ts` is the vocabulary: **Life Transformer** (a trainer), **Studio Leader** (`StudioLeader`, `HeadTrainer`), **Studio Owner** (`StudioOwner` — a studio-tier role since My Studio, Sep 18), **Franchise Owner** (`Owner`, `FranchiseOwner`), **Founder / Overseer**, **System Administrator**. Three tiers (AJ, Sep 18): the **studio tier** runs one studio — head trainer, studio leader, studio owner at that studio, or a trainer with **the grant** (`Trainer.managedStudioIds`); the **owner tier** runs several; the **company tier** sets the standard. `leadsHere()` (`features/relay/leads.ts`) is the one app-side answer to "runs this studio" and mirrors `trainerLeads` in the rules. Operations is reachable by studio leaders and above (head trainer and above, AJ, Sep 18); the grant opens My Studio's leader sections, not Operations; the **Admins dashboard** is administrators (`Admin`, `Founder`) only — corporate staff who set up studios and set the standard, above the franchisees. Details: `docs/business/roles-and-permissions.md`.

**Always on, whatever you touch** (each is spelled out in full in that file):

- **A screen holding typing registers with `useUnsavedChanges`,** and any new way of switching screens, tabs or sections asks the gate first (`useLeaveGuard` or a leave scope), or the typing vanishes unannounced. See `src/features/unsaved-changes/README.md`.
- **Never block a save.** End Session confirms; it does not refuse. Only `performed` sets count toward any average - read outcomes through `src/lib/set-outcome.ts`.
- **Firestore refuses `undefined`.** Strip it before a write (`withoutUndefined`).
- **Use the Auth uid, not `authTrainer.id`,** for anything a rule pins to the signed-in person. The two differ on older accounts.
- **Mindbody routes need `authedFetch`;** a plain `fetch` gets a 401. The web service has no Firestore admin key.
- **Never write a whole client object back** - `clients/{id}.renewal` belongs to the nightly job and the rules refuse the write.
- **A menu item is not a gate, and a sign-out forgets the person.** A screen a role may not open checks on the screen (`mayOpenOperations`), not only in the menu; a module-level memory of what someone was doing registers `forgetOnSignOut` (`src/features/sign-out/`).
- **Two files whose names differ only by case are ONE file on Windows.** Before shipping: `git ls-files | tr A-Z a-z | sort | uniq -d` prints nothing.
- **Run the suite with `TZ=America/New_York`.** A date-only ISO string is UTC; a date-time with no zone is local.
- **A green typecheck, suite and build do not mean a screen mounts.** Only `*.render.test.tsx` files mount anything; add one for any component that does work during render or in a layout effect.
- **Never type a raw control or invisible character into source;** write the escape.
- On AJ's PC, Claude's shell can run git and `tsc` but not `vitest` or `vite`; the cloud container can run everything except `test:rules`. **AJ's `test:rules` run is the one that counts.** Use `git --no-optional-locks` for read-only git commands on the PC mount - a plain `git status` leaves an `index.lock` behind that cannot be deleted without delete permission and blocks his next git command.
