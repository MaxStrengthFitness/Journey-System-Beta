# Demo Mode — Sep 20 2026

**A real studio that everybody can enter, full of people who do not exist.**

Branch `claude-experiment`, six commits (`Demo 1` … `Demo 6`). Rebuilt from
scratch against current `master`; the retired `demo-mode-foundation` branch
(tag `archive/demo-mode-foundation`, 259 commits behind) is not merged and not
used.

AJ's brief, Sep 20: *"Let's compile together a demo mode that can be accessed
by selecting the demo studio which every user will have full access to."* With
his answers: demo trainers get their own records, one deploy, and the boss sees
it on the live Render URL.

```
1.  firebase deploy --only firestore:indexes
2.  npm run test:rules                      ← the gate. Needs JDK 21.
3.  firebase deploy --only firestore:rules
4.  git checkout master && git merge claude-experiment

7.  open the app, sign in, and press "Set up Demo Mode"
       on the studio selection screen, under Practice
```

**Why the rules go first.** They only *add* access, so deploying them before
the app means the running app is unaffected and the new one finds its rules
waiting. The reverse order gives every trainer a broken "Set up Demo Mode"
button for however long the two deploys are apart.

**Step 2 is the real gate, and it has not run.** The emulator jar downloads
from a host the cloud container is blocked from, so `npm run test:rules` has
never seen these rules. The suite has 13 new assertions for Demo Mode, most of
them "denies". A structural lint (`tests/firestore.rules.lint.test.ts`) runs in
the ordinary suite and confirms the file is still syntactically whole, which is
not the same thing as correct.

**Step 7 takes a moment** — it writes 1,202 documents in four batches. If it
fails half way, press it again: every id is derived, so a second run finishes
the job rather than starting a second demo.

**Nothing exists until step 7.** The demo studio is not in the repo; it is a
Firestore document the seeder creates. Before that, the Practice section on the
studio selection screen offers the button and nothing else.

## The one decision everything follows from

**The demo studio is a real studio document, and demo data lives in the
ordinary collections.**

The alternative — a parallel set of `demo*` collections, or a client-side
fixture layer — was rejected on the earlier branch and is rejected again for
the same reason. Every screen in this app reads real collections scoped by a
studio id. A parallel store means a second code path through every screen, and
a second code path is a second thing to keep true. Within a month the demo
would be showing a version of the app that no longer exists.

So `studios/demo-studio` is a studio like Solon is a studio. The Journey grid,
the renewal pipeline, the attendance watch, Machine fit, Operations — all of it
works inside Demo Mode because none of it knows it is in Demo Mode.

What keeps it separate is not a wall around the data. It is three things: the
id (`demo-studio`, fixed, never generated), the guards in
`src/features/demo-mode/`, and the Firestore rules that name it.

## Full access is authorisation, never membership

The tempting one-liner was to make `worksAt()` and `leadsStudio()` return true
for the demo studio. Done in a minute, opens everything. It is wrong, and the
reason is worth writing down because it is not obvious.

Those two functions answer a different question depending on who is asking:

| | Subject | Demo answer |
| --- | --- | --- |
| "May I act here?" | the signed-in trainer | **yes** |
| "Is this person on this studio's team?" | every trainer in the company, filtered | **no** |

Operations → Renewals (`AdminRenewalsTab.tsx:78`) and the Delight queue
(`DelightQueue.tsx:94`) both build their people lists the second way. A blanket
true would have put the entire company staff directory on Demo Mode's team
screens — which is precisely what demo trainers exist to avoid.

So membership stays honest, and `hasRunOfDemo()` widens **authorisation** at
six call sites: `canManageRenewals` (which carries `leadsHere`, and with it
Relay, My Studio and StudioHub), `leadsStudioPerRules`, InBody record and
remove, note sharing, `operationsStudios`, and the App Mode switch.

The Firestore rules do the same thing, and there the blanket widening IS
correct — rules can only ever be asked about the caller.

## One realm at a time

`studiosInRealm()` is applied last in `operationsStudios()`:

> **From inside Demo Mode you see Demo Mode and nothing else. From anywhere
> else you do not see it at all.**

That single rule is the entire demo boundary in Operations — there is no check
in any of the nine tabs. An administrator's "every studio" cannot fold practice
numbers into the company's, and inside Demo Mode there is one studio in the
list, so `canSpan` is false and "All my studios" does not appear.

## The two crossings fail in opposite directions

| Crossing | Example | What it costs | How it fails |
| --- | --- | --- | --- |
| Real data reached **from** Demo Mode | a trainer practising deletes a client, and it is a real one | destroys something | **throws** (`DemoBoundaryError`) |
| Demo data reaching **real** systems | practice sessions in a studio's numbers; a demo client pushed to Mindbody | the numbers quietly stop being true | **skips** (`skipsForDemo`) |

The second is the more dangerous in practice because nobody notices. It skips
rather than throwing because a nightly job that threw on the demo studio would
take the real studios queued behind it down with it.

`isDemoRecord()` checks **four** field names — `studioId`, `homeStudioId`,
`hostedAtStudioId`, `clientHomeStudioId` — because this app genuinely spells
"the studio this belongs to" four ways on documents, and a guard that checked
one of them would leak.

## The two leaks that would not have looked like leaks

Everything above is about a trainer reaching real data. These two are the other
direction, and they are the half that does not announce itself.

1. **`server/machine-trends-job.ts`** reads `exerciseLogs` across the whole
   company with no studio filter — deliberately, because "how this machine is
   used" is a company-wide answer. 910 demo sets would have become part of what
   Max Strength believes about its own equipment from the first weekly run.
2. **Machine fit's company tier** pools every studio's fit index, and its cells
   are k-anonymous at five clients. Six demo clients at one height is enough to
   form a cell, and the guidance a real trainer then reads would be partly
   about people who do not exist.

Both are dropped in the **pure aggregator** (`buildMachineTrends`,
`buildCompany`), not in the query: whether a row counts belongs with the other
rules about what counts, and doing it there covers every caller. No job, no
query and no schema changed.

**The names** are Lord of the Rings, from the **films** rather than the books,
using the most ordinary names the Fellowship has — Frodo, Sam, Merry, Pippin,
Rosie — and, where the films leave a character with no surname, the name the
films themselves attach: Arwen *Evenstar*, Éowyn *of Rohan* (Rohan is an
ordinary surname in its own right), Aragorn *Strider*. A demo can be a little
silly; it just must not be a joke, so Gandalf and Legolas are out on AJ's word
and so is every title. A test enforces it. Every email is `@demo.invalid`, a
reserved TLD (RFC 2606) that can never route anywhere.

**Every client's sessions + remaining sessions equals a real package size**, so
`count − remaining` on the Mindbody side is exactly what Journey has recorded.
Rosie is 45 done of a 48 with 3 left. Before that she would have shown 24
sessions on her profile and 45 used in Renewals — the one question in a demo
you cannot answer. She is also the only client inside the conversation window,
so the pipeline has one row and one story.

Her package is seeded as the **input** the renewals engine reads, not as a
finished snapshot: the nightly job rebuilds that snapshot and replaces whatever
is there. Seeding the answer would be seeding something that gets overwritten;
seeding the question means the job keeps producing the same one. The demo
studio is `mindbodyMode: "offline"` with no site id, so the job never queues a
pull for it.

## How a weight actually moves

This is the part a generated history gets wrong by default, and gets wrong in
the way that would embarrass the demo. A naive "+5 lb every third session" has
a 72-year-old more than doubling her leg press inside a year.

What really happens here (AJ, Sep 20 2026): clients train **twice a week for
twenty minutes**, one set to failure, and they are typically **over forty**.
So most sessions the weight does not move at all; when it does it moves **2 to
6 lb**, and not often; and the only large corrections are early, while the
trainer is still **finding** the client's working weight for that machine —
those can be up to 20 lb, because the starting guess was a guess.

Two things the model has to get right beyond the rates:

- **Routines alternate A and B, and a machine lives in only one of them.** A
  client with 45 sessions has performed each machine about 22 times, not 45.
  Every rate is per performance of that machine.
- **The increment scales with the load.** A flat 2-to-6 lb is right on a leg
  press starting at 160 and nonsense on an overhead press starting at 15,
  where six pounds is a forty per cent jump no trainer would make. Five per
  cent of the starting load lands inside AJ's band on every machine in the
  catalog; the finding correction is a fifth of it, capped at 20.

The result reads like a real client: `50 → 50 → 50 → 50 → 50 → 50 → 50 → 50 →
50 → 50 → 50 → 50 → 50 → 50 → 53 → 53 → 53 → 53 → 53 → 53 → 53`. Six tests
police it, including one that fails if weights move on more than 30% of
performances and one that fails if anybody doubles.

## Determinism is the design

Every id is derived and every number comes from a PRNG seeded on that id.

1. **The seeder is its own reset.** "Set up" and "Reset" are one button, and a
   run that dies at document 700 is fixed by pressing it again. Nothing has to
   be deleted first. There is deliberately **no wipe**: deleting a thousand
   documents from a browser is slow, partial failures leave the studio in a
   state no code describes, and it is a loaded gun pointed at a collection that
   also holds real clients. Overwriting reaches the same place with nothing to
   aim.
2. **The demo is identical everywhere** — AJ's laptop, Render, a trainer's
   iPad — so "look at Arwen's profile" means the same thing in two rooms.
3. **It can be tested at all.** A history that changed every run could only be
   eyeballed.

Timestamps are emitted as a `{ __ts }` sentinel that each writer converts,
because an ISO string where a Timestamp belongs silently removes the document
from every `createdAt` range query — Insights, Hours, Exports, machine trends.
A plain string in the seeder's output is now always deliberate.

- **`firestore.staging.rules` is untouched.** It is a 571-line fork that
  already denies 32 of the collections the app uses and has no tests — Phase 1

  all. Adding demo clauses to it would make a broken file marginally less
  broken.
