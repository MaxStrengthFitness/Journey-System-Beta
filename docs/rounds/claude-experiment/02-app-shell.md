# 02 — The application shell

Routing, global state, app-wide data streams, navigation, auth, studio selection, the header and the bottom bar. Read on `master` at a064019 (Sep 20 2026). Every file:line below was read, not inferred; the bundle numbers come from a `vite build` into the scratchpad (nothing under the repo was written).

---

## 1. What this area does — my interpretation

**Boot.** `index.html` buffers early errors, then `src/main.tsx` mounts `<StrictMode><ErrorBoundary><ThemeProvider defaultTheme="dark"><App/>` and installs the only window error/rejection reporters (capped at 50 POSTs to `/api/log-error`, mirrored into a 10-item ring buffer the feedback drawer reads). `main.tsx` also statically imports seven feature stylesheets, so the journey-grid, equipment, calendar, Pulse, catalog and studio-tasks CSS are in the one 400 kB (60 kB gz) stylesheet regardless of which screen is open. `src/firebase.ts` initialises Firestore at module scope with `persistentLocalCache` + `persistentSingleTabManager` (multi-tab was switched off after the SDK's `b815` assertion storm) and registers the id-token source for `authedFetch`.

**Auth and the first three collections.** `App.tsx` runs `useAuthInitialization` (`src/hooks/useAuthInitialization.ts`): on `onAuthStateChanged` it awaits, strictly in series, the id token, `trainers/{uid}`, an email-keyed fallback query with the claim-on-sign-in (`features/trainer-identity/claim.ts`), a forced token refresh if the claim's role disagrees with the document, then `getDocs` of `studios`, `trainers` and `networks`. Only then is `isAuthReady` true and the provider stack mounts: `MindbodyHealthProvider` (one listener on `system/health`), `ToastProvider` (which also publishes `window.__showToast` for `lib/firestore-errors.ts`), and `ActiveStudioProvider` (`src/contexts/ActiveStudioContext.tsx`), which restores `activeStudioId` from `localStorage["max_strength_active_studio_id"]`, derives `availableStudios`, sets the studio's timezone into the module-global `lib/studio-time.ts` during render, and paints the studio's `brandColor` onto `--cta`.

**The god file.** `src/AppContent.tsx` (2,615 lines) is then everything at once: 27 `useState`, 8 `useEffect`, 8 `useMemo`, 3 `useCallback`, 13 `lazy()` views, and the app-wide streams — `useTrainers`, `useStudios`, `useNetworks` (whole collections, re-subscribing to what `useAuthInitialization` just fetched), `useMachines` (whole `machines` collection merged over the legacy `DEFAULT_MACHINES`), `useLiveSchedule` (a three-day live window plus a fetched week-ahead cache), `useStudioRoster` (`clients where homeStudioId == studio`, limit 1500, plus booked visitors by id), `useSessions` (the studio's last 24 hours), plus `useAutoSync` (the iPad-side Mindbody pull-sync lease). `clients` is memoised as the roster plus the selected client's one-shot `getDoc`. Before the shell renders, `AppContent` returns early in this order: no `user` → `LoginScreen` (Google / Microsoft with a `@maxstrengthfitness.com` check); no `authTrainer` → `AccessRequestView`; no active studio or `isChangingStudio` (unless the view is one of the two dashboards) → `StudioSelectionView` (which pins a default studio per device via `lib/default-studio.ts`); an onboarding name → `CreateClientModal` full-screen. A pinned-studio effect (lines 331–357) skips the picker for a device bolted to one floor.

**Navigation.** There is no router and no `pushState`. One `useState<View>("clients")` (`currentView`, 17 ids in the `View` union in `src/types.ts:1820`) is switched on by a chain of 15 conditionals inside `<Suspense><AnimatePresence mode="wait">` at lines 1538–1855; `setCurrentView` is called 39 times in this file alone and is passed down as `setView`, `onViewChange`, `onNavigate`, `onOpenClientTask`, `onComplete`, `onBack` and friends. A second state `appMode` ("trainer" | "admin") swaps the bottom bar between six trainer tabs (Hub · Client · Start/Resume Session · Learning · My Studio · Calendar) and one or two admin tabs (Operations · Admin). Where the trainer *is* is really five states that must agree: `currentView`, `appMode`, `selectedClientId` (+ its fetched doc and `resolvedClientId`), `selectedReportId`, `selectedProfileTrainerId`, plus per-feature memory (`lastLearningView`, `learningJump`, Relay's `requestPlanner` intent, My Studio's `section-memory`, the profile's `sessionStorage` handoff). On a refresh every one of those resets to its default: the app lands on the Hub in trainer mode with no client, the studio comes back from localStorage, the theme from localStorage, and a live session is only *offered* (the Start tab reads "Resume…" via `lib/live-session.ts`) — it is one tap away, never automatic.

**The header and the bar.** `components/AppHeader.tsx` draws the logo, the studio-name button (switch studio), the header search (whose results render on the Hub — the term lives in `AppContent`), and the icon cluster built in `AppContent` (refresh schedule → `syncMindbodySchedules` from the iPad, `ThemeToggle`, `FeedbackButton`, `PlannerReminders`, `NotificationBell`, the gear → `trainer-hub`), then the initials dropdown (App Mode: Trainer · Operations · Admin for `isStudioLeader`, View Profile, Switch Trainer, Switch Studio, Log Out Facility). The header is hidden on `workouts`; the tracker draws its own and receives the same `rightControls` / `trainerDropdown` elements as props. `components/NavButton.tsx` is one tab.

**What else the shell owns.** Four overlays live at the bottom of `AppContent`: the Machine Info "Deep Dive" dialog (lines 1978–2416, edits `machines/{id}`), the New Clients dialog (2418–2492), the Trainer Reorder dialog (2494–2600, writes `trainers/{id}.order`), and the "Wipe Entire Database" `StrongConfirmationModal` (2602–2610) whose `executeAppCleanse` (943–987) deletes every document in eleven top-level collections from the browser. It also owns sign-in (`handleLogin`, 1064–1154), the catalog re-seed (`handleRestoreMachines`, 1005–1026, which is why the 140 kB `data/machine-definitions.ts` is in every trainer's entry bundle), `handleManualRefresh` for the Admins dashboard, the studio patcher `updateStudio`, and a 20-field client edit form state (`clientFormData`) with its submit and parse handlers. Two admin-only URL/console back doors also live here: `?view=trainer-hub` (870–899) swaps `authTrainer` to the first owner-role trainer, and `App.tsx:44` exposes `migrateClientMachineMetrics` on `window`.

## 2. Anomalies — the irregular, clunky and suboptimal

### A. Safety and correctness

**1. Critical — the production database can still be wiped from an iPad with one typed phrase, and the wipe is neither complete nor honest.**
`src/AppContent.tsx:943–987` (`executeAppCleanse`), reached from Admins → System tools → "Wipe" (`src/features/admin/system/AdminSystemToolsTab.tsx:178`) through `StrongConfirmationModal` (phrase `confirm wipe system`, `AppContent.tsx:2606`). The rules let a super admin delete every one of the eleven collections (`firestore.rules` `studios`/`trainers`/`clients` delete: `isSuperAdmin()`). **Why it matters:** already known (§2.8 #7, "beta must not"), and beta is now live on `master` (Sep 19). What §2.8 does not say: it fires one `deleteDoc` per document inside a `Promise.all` per collection, so a single refusal or a quota hit mid-loop leaves a half-deleted estate; it deletes only top-level documents, so `clients/{id}/ford`, `inbodyScans`, `sharedNotes`, `studios/{s}/roster`, `renewals`, `watchlist` are all orphaned; it deletes the admin's own `trainers/{uid}`; and the modal copy promises it "will then completely re-initialize the 20 standard machines" while the code preserves machines and re-initialises nothing (`AppContent.tsx:969`, `:2605`). **Direction:** a destructive operation of this size belongs in `scripts/` behind the service account with a dry run, or nowhere; the browser button should go before the next deploy.

**2. High — an admin-only URL parameter impersonates another trainer, and a mock "Owner Tim" profile ships in the bundle.**
`src/AppContent.tsx:881–897`: with `?view=trainer-hub` and an Admin/Founder/Overseer token, `setAuthTrainer(trainers.find(isOwner) || trainers[0])` replaces the signed-in person's profile with someone else's; if no trainers are loaded it fabricates `{ id: "owner-temp", fullName: "Owner Tim", initials: "TD", role: "Owner" }`. `ActiveStudioContext.tsx:212` and `AppContent.tsx:915` still special-case `"owner-temp"`. **Why it matters:** every `authorId`/`trainerId`/`trainerInitials` written after that carries the other person's identity (the rules pin only what is keyed by Auth uid); and this is "emergency admin access" from the PIN era that no runbook mentions. **Direction:** delete the branch and the two `owner-temp` guards; emergency access is a role on the trainer document, not a query string.

**3. High — a hard-coded personal e-mail in the shipped client creates an Admin profile.**
`src/hooks/useAuthInitialization.ts:173–194`: if no trainer document is found and the address equals `jurgensaj@gmail.com`, the browser writes `trainers/{uid}` with `role: "Admin"`, `primaryHomeStudioId: "system"`; if the write is refused it keeps the in-memory Admin profile anyway ("Fallback dynamic profile if writes fail"). **Why it matters:** KNOWN-TRAPS records the picker's hard-coded e-mail as removed; this one survived. It is a bootstrap path in production code, readable by anyone who opens the bundle, and it hands out an unwritable phantom Admin whose studio is `"system"`. **Direction:** bootstrap once with `scripts/` and the service account; delete the branch.

**4. High — "Switch Trainer" dead-ends a signed-in trainer on the Request Access form until they log out or reload.**
`src/AppContent.tsx:932–935` (`handleTrainerLock` sets `authTrainer` null and removes `max_strength_trainer_id`), offered on every screen at `:1469–1475`. With `authTrainer` null the early return at `:1167` renders `AccessRequestView` with only `onLogout` (no `onClose`), and the restore branch at `:901–907` cannot fire because the key was just removed. **Why it matters:** a menu item in the header of every screen — including the tracker's header — leads to a screen that asks a working trainer to "request access" with their own name pre-filled. The item is a relic of trainer PINs, which the comment at `:347` says are gone. **Direction:** remove the item, or make it a real "Log out" (the iPad's device lock is the gate, as the same comment says).

**5. High — the app-wide `machines` stream silently drops any catalog machine without an `order` field, and the new catalog editor never writes one.**
`src/hooks/useMachines.ts:14` queries `orderBy("order", "asc")`; Firestore excludes documents that lack the ordered field. `src/features/admin/machines/CatalogMachineEditor.tsx:82` writes `defaultOrder`, never `order`; `MACHINE_DEFINITION_LIST` (the re-seed at `AppContent.tsx:1005–1026`) has 0 `order` keys and 20 `defaultOrder` keys. `src/hooks/useMachineCatalog.ts:12–15` says in its own comment why *it* does not order ("Firestore's orderBy silently drops documents missing the field, so a machine created without defaultOrder would vanish from the app"). **Why it matters:** a machine added in Admins → Catalog appears in the Catalog (which uses `useMachineCatalog`) and is absent from every screen fed by the shell's `machines` prop — 10 screens including the Active Session, the routine builder and the consultation wizard. Two hooks on one collection, one of them carrying the trap the other documents. **Direction:** drop the `orderBy` in `useMachines` and sort in memory (as its sibling already does), then retire one of the two.

**6. High — the whole shell sits inside one error boundary, so a render error anywhere takes the Active Session down with it.**
`src/AppContent.tsx:1498` wraps header, main, nav and all four overlays; the only inner boundary is the Calendar (`:1797–1841`); `grep` finds no other `<ErrorBoundary` in `src/`. The fallback (`components/ErrorBoundary.tsx:57–110`, `// @ts-nocheck`) offers "Reload" (`window.location.reload()`) and "Back to Studio Hub" (`window.location.href = '/'`). **Why it matters:** the floor is Rank 1. A throw in the notification sheet, the feedback drawer, a Suspense child or a layout effect (KNOWN-TRAPS names one JourneyGrid `ResizeObserver` use that still does not feature-detect) replaces the tracker with a crash page mid-set; reload loses the note draft's in-memory state and costs the chunk download again on studio Wi-Fi. **Direction:** a boundary per routed view (and one around each header overlay) whose fallback keeps the nav and offers "back to the session"; the shell boundary becomes the last resort.

**7. Medium — the Machine Info "Deep Dive" dialog is unreachable and is full of invented numbers.**
`src/AppContent.tsx:1978–2416` renders only when `infoMachineId` is set, and the only setter is the `onOpenInfo` callback at `:1665–1668` passed to `WorkoutTrackerView`, which declares the prop (`WorkoutTrackerView.tsx:219`) and never calls it. The dialog itself carries "Age 20-30 · Female | Beginner · Average Weight (45 lbs) · SD ±5", three named trainers' cues, a "Send Resource to Client" button (an outreach the product forbids) and a "Log Session / Add Data Points" button that does nothing (`:2205–2211`, `:2405–2408`). **Why it matters:** 440 lines of Gemini-era mock UI in the entry bundle of every trainer, one wiring change away from showing fabricated cohort statistics — the exact opposite of "sentences, not scores". **Direction:** delete it; the machine's real page is Learning → Catalog.

**8. Medium — the Hub's client edit form, the session-count stepper and the tracker's client picker are unreachable, and the state for them lives in the shell.**
`clientFormData` (`AppContent.tsx:736–756`), `startEditClient` (`:758–805`), `handleClientSubmit` (`:818–852`) and `editingClient` exist for `ClientsView`, which declares `startEdit` and `updateSessions` (`components/ClientsView.tsx:165–166`) and never calls either; its `setEditingClient` is only ever called with `null` (`:976`), so the 360-line form at `ClientsView.tsx:625–983` cannot open. `showClientPicker` (`AppContent.tsx:854`) is never set true anywhere, so the first `ClientSelectionDialog` in the tracker (`WorkoutTrackerView.tsx:2874–2883`) is dead; `setClientFormData` is declared by the tracker (`:218`) and unused. `useClientMutations.submitClientFormData` (`src/hooks/useClientMutations.ts:122–167`) — the only path that would create a client with `addDoc` and a random id, no `homeStudioId` — and `updateClientSessions` (`:169–182`, writes `remainingSessions`, a field KNOWN-TRAPS says nothing keeps current) are therefore dead too. **Why it matters:** ~600 lines and a 20-field state object maintained for nothing, plus a latent writer that violates "a client lives at `clients/{mindbodyClientId}`". **Direction:** delete the four states, the three handlers, the two mutations, the form and the props.

**9. Medium — seven props are passed to Operations that its shell explicitly discards, so the New Clients dialog and `updateStudio` are dead as well.**
`src/features/admin/AdminDashboardView.tsx:108–116` (`void newClientsCount; void onShowNewClients; void onUpdateStudio; void onUpdateClient; void onRestoreMachines; void onReorderTrainers; void onAppCleanse;` — "so AppContent's call site needs no change"). `newClientsThisMonth` (`AppContent.tsx:663–673`, a per-render filter over the whole roster on Journey's `createdAt`, which during the migration means "documents the sync created this month", not new clients), the New Clients dialog (`:2418–2492`) and `updateStudio` (`:807–816`) have no other reader. **Direction:** remove them from both sides; the two dashboards should take what they use.

**10. Medium — a quota error freezes every stream silently and permanently.**
`AppContent.tsx:412–430` listens for `window.error` messages containing "quota" and sets `hasQuotaError`; `:475` folds it into `isDataReady`, which unsubscribes every app-wide hook; nothing ever sets it back, and the only reader is `ClientProfileView`, which just disables its own streams (`ClientProfileView.tsx:482,551,573`). No banner, no retry. Firestore listener errors do not reach `window.error` at all (they go to the `onSnapshot` error callback, where `lib/firestore-errors.ts:60–65` swallows quota with a `console.warn`), so the switch fires on almost nothing — and when it does, the iPad shows yesterday's roster with no sign anything is wrong. **Direction:** delete the kill-switch, or make it a visible, time-limited backoff like `useStudioRoster` already implements for itself.

**11. Medium — a stream error shows a raw developer message and the listener never comes back.**
`src/lib/firestore-errors.ts:88–101` toasts `Firestore Action Failed: get on trainers. Error: Missing or insufficient permissions.` (uppercase, 12px, bottom-right, over the Calendar tab) — or a native `alert()` if the toast bridge is absent — and `useTrainers`/`useStudios`/`useNetworks`/`useMachines`/`useSessions`/`useLiveSchedule` never re-subscribe after an error (Firestore terminates an errored listener). Only `useStudioRoster` retries. **Why it matters:** "a failed read means unknown, never empty" is honoured in the roster and nowhere else in the shell; a trainer sees a sentence in the app's own jargon and a screen that quietly stops updating. **Direction:** one retry policy for every app-wide stream, and one plain sentence ("Journey can't reach the studio's records — showing what it last saw").

**12. Medium — the selected client is a one-shot `getDoc`, so a visiting (cross-train) client's profile and session read stale data.**
`AppContent.tsx:432–468` fetches `clients/{selectedClientId}` once; the `clients` memo (`:553–564`) lets a roster copy win when the client is home-studio, but a visitor's copy is that snapshot (or `useStudioRoster`'s 15-minute visitor re-read). Neither `ClientProfileView` nor `WorkoutTrackerView` streams the client document — both `clients.find(...)` (`WorkoutTrackerView.tsx:693,1023`), and the tracker writes to `clients/{id}` at `:1006` and `:1117` that will not reflect back. **Why it matters:** cross-training is the case the "sessions are scoped by client" decision exists for; the shell serves that client worst. **Direction:** a per-client document listener owned by the profile/tracker (they already open seven journal listeners each), and the shell stops fetching clients at all.

### B. Data streams and cost

**13. Medium — `trainers`, `studios` and `networks` are read twice on every cold start, in series, before anything paints.**
`useAuthInitialization.ts:225–257` awaits `getDocs` of the three collections one after another (after four earlier serial awaits), then `AppContent.tsx:477–479` opens `onSnapshot` on the same three. Six to eight sequential round trips on studio Wi-Fi before `isAuthReady`, with the `trainers` and `networks` failures swallowed by empty `catch (e) {}` blocks (`:248`, `:257`) — a failed `trainers` read yields `[]`, which the shell treats as "no trainers". **Direction:** the listeners are the source of truth; `useAuthInitialization` should load only `trainers/{uid}` and let the shell stream the rest (in parallel, with an error state).

**14. Medium — the schedule listener is unscoped when no studio is active, and there is a real path to that state.**
`src/hooks/useLiveSchedule.ts:245–248` adds `where("studioId","==",…)` only `if (activeStudioId)`; the studio picker's "Go to Operations" (`AppContent.tsx:1201–1205`) and the early-return exception at `:1182–1186` render the shell with `activeStudioId === null`, so the three-day window is read for all four studios. `useSessions.ts:23–26` fixed exactly this for sessions and says why. **Direction:** the same rule — ask for nothing until you know where you are.

**15. Medium — `hub_announcements` and `trainers/{uid}/notifications` are streamed whole, unbounded, to every iPad, and each read stamps every document.**
`src/features/notifications/useHubAnnouncements.ts:72–74` (`query(collection(db, "hub_announcements"))` — no `isActive`, no expiry, no limit, every studio's), `useNotifications.ts:31–33` (whole subcollection, display capped at 50 but read in full). `markAnnouncementsRead` (`useHubAnnouncements.ts:118–133`) does `arrayUnion(readerId)` per document per reader, and each stamp re-sends that document to every listening device: cost ~ trainers × announcements × devices. Both hooks empty their list on error (`:61`, `useNotifications.ts:42`). **Direction:** query active + unexpired announcements scoped to the studio/network with a limit; move reads to a per-trainer `read` map; keep the last value on error.

**16. Medium — the roster listener ships whole client documents, and the `Client` document is enormous.**
`src/hooks/useStudioRoster.ts:112–118` streams every `clients where homeStudioId == studio` (limit 1500; ~300 at the largest studio). `Client` (`src/types.ts:642–943`) carries `machineStats` for every machine, `mindbodyContracts`, `mindbodyServices`, `renewal`, `goalHistory` (≤30), `events`, `subjectiveSnapshot`, `inbodySummary`, `currentMachineMetrics`, `trainerTally` … so every completed session (which bumps `trainerTally`, `sessionCount`, `machineStats`) re-pushes a multi-kilobyte document to every open iPad at the studio, and the nightly renewals job re-pushes all of them. Rough cold-load per iPad: ~300 client docs + ~100–150 live bookings + ~250–400 fetched bookings + 30–50 trainers + machines + studios + networks + announcements + notifications ≈ **700–1,000 documents, plausibly 3–6 MB**, before the first screen is useful; then a steady trickle proportional to the studio's whole day. The comment at `studio-roster.ts:43–48` already warns the FileMaker import will grow it. **Direction:** a thin roster projection (id, names, home studio, `renewal` summary, flags) for lists, and the full document only where a client is open; or at minimum filter to active clients now, before the import.

**17. Low — the 24-hour sessions window never re-anchors.**
`src/hooks/useSessions.ts:14–15` computes `twentyFourHoursAgo` once per effect run; an iPad left signed in for a week streams a week of sessions. `useLiveSchedule` solved the same thing with `dayTick` (`useLiveSchedule.ts:96`, `:268–271`). **Direction:** reuse the day-roll.

**18. Low — three hooks and the shell each stream the `machines` collection in their own shape.**
`useMachines` (legacy `Machine`, merged over `DEFAULT_MACHINES`), `useMachineCatalog` (`MachineCatalogEntry`, 12 call sites), `useStudioMachines` (resolved roster, 14 call sites, mounting `useMachineCatalog` each time). Already known (§2.7 "layers, not copies"); what is new is that the shell's layer is the one with the `orderBy` trap (#5) and the one initialised from the *legacy* seed, so a screen sees `DEFAULT_MACHINES` for a beat before the catalog answers. **Direction:** the shell should not stream machines at all once the tracker reads the roster (the ROADMAP item); until then, one hook.

### C. Navigation, state and the early-return chain

**19. High — "Switch Studio" from the header does nothing on Operations, then the picker appears later, unasked.**
`AppContent.tsx:1182–1186` skips the studio picker while `currentView` is `admin-dashboard` or `admins-dashboard`, but the menu item (`:1477–1483`) and the header's studio button (`:1527`) still set `isChangingStudio = true` there; nothing resets it, so the moment the trainer returns to any trainer view the picker takes over the screen. **Direction:** on the two dashboards the studio button should open the Operations scope control (which is the studio switch there since the Operations round), and `isChangingStudio` should be cleared when it is not honoured.

**20. High — where the trainer is is five independent states that are set from 39 call sites, and nothing keeps them consistent.**
`setCurrentView` × 39 in `AppContent.tsx`; `appMode` is set in 4 places and forgotten by the rest: `TrainerSettingsView`'s "Open Operations" (`features/settings/TrainerSettingsView.tsx:341`) and `NotificationBell`'s `onNavigate` (`AppContent.tsx:1367`, `setCurrentView(view as any)`) switch the view without switching `appMode`, so Operations renders over the six trainer tabs with none active; `openClientTask` (`:1626–1638`) picks a view by string; `resumeLiveSession` (`:700–729`) is a five-way branch that ends in `client-directory`. Seven `as any` casts on view ids that are already in the union (`:1367,1424,1437,1792,1935,1950` …) hide this from the compiler. Already known in outline (§2.1, §4.3 "Routing and state: not started"); what is new is that the number of views (16 routed) and the number of cross-screen jumps (bell → client/Learning/Relay, Relay → client/report/wizard, Operations → profile/My Studio, Learning refs from notes and announcements, `section-memory`, the profile's `sessionStorage` handoff) has already produced four ad-hoc "intent" mechanisms. **Direction:** one navigation reducer with a typed `Location` (view + params + mode derived from the view), one `navigate()` handed down, and the URL as its serialisation — see the questions.

**21. Medium — nothing survives a refresh except the studio and the theme, and a live session is one tap away rather than resumed.**
Keys actually read: `max_strength_active_studio_id` (`ActiveStudioContext.tsx:69`), `max_strength_default_studio_id` (`lib/default-studio.ts`), `journey-system-theme` (`ThemeProvider.tsx:30`), `max_strength_active_session_id` (`lib/live-session.ts:28`, read only when the Start tab is tapped, `AppContent.tsx:712`). `max_strength_trainer_id` and `max_strength_authenticated` are written in three places (`:346–349`, `:1196–1197`, `App.tsx`/`ActiveStudioContext.tsx:72–74`) and read by nothing that can fire (see #4); `ActiveStudioContext.isAuthenticated` has zero consumers. `handleLogout` (`App.tsx:35`) and the context's unused `logout` (`ActiveStudioContext.tsx:161–169`) both `localStorage.clear()`, which also resets the trainer's theme choice. **Why it matters:** "we need the app to be able to act as pen and paper in terms of reliability" — a Safari refresh mid-set (a real event on iPadOS) drops the trainer on the Hub. **Direction:** persist `{view, clientId, sessionId}` and restore into the tracker when the remembered session is still `In-Progress`; delete the two dead keys and the dead context fields.

**22. Medium — `availableStudios` reads `networks` but does not depend on it.**
`src/contexts/ActiveStudioContext.tsx:106–141`: deps `[authTrainer, studios, isAdmin]` while the body loops `networks`. A franchise owner whose `networks` snapshot lands after `studios` sees a stale list until something else changes; the context value object is also rebuilt every render (`:221–238`), re-rendering all 40 `useActiveStudio()` consumers on every provider render. **Direction:** add the dependency (or derive with `useMemo` on all inputs) and memoise the value.

**23. Medium — `lib/permissions.ts` is 333 lines of which ~40 are used, and "is this an Admin" is spelled out inline six times.**
`hasPermission` (`:162–332`), `isStudioInTerritory` (`:115–139` — the very function §3.4 describes as "the app-side" partition), `areStudiosInSameNetwork`, `isLifeTransformer`, `isFranchiseOwner`, `isAdmin(trainer, tokenRole)` have **zero** callers; `isSuperAdmin(trainer, currentUserEmail)` (`:98–103`) passes an *e-mail* into the `tokenRole` slot. Meanwhile the same 4-way `tokenRole === "Admin" || authTrainer?.role === "Admin" || …` is repeated at `App.tsx:71–76`, `AppContent.tsx:875–880`, `:1577–1582`, `:1823–1828`, and `ActiveStudioContext.tsx:111–115` adds `Overseer` to its copy; the studio picker's `hasAccessToStudio` (`StudioSelectionView.tsx:306–319`) is a fourth spelling that ignores `ownedStudioIds` and networks, so an owner can see a studio the context would let them into and not be able to enter it from the picker. Four role modules coexist (`lib/permissions.ts`, `features/renewals/permissions.ts`, `features/learning/permissions.ts`, `features/relay/leads.ts`). Already partly known (§3.4 says the app-side check exists — it does not, nothing calls it). **Direction:** one `roles.ts` that mirrors the rules (`leadsHere`, `worksAt`, `isEveryStudioRole`, `isAdminTier`) fed by `tokenRole ?? document.role`, and delete the rest.

**24. Medium — `authTrainer`, `trainers`, `machines`, `clients`, `studios` are threaded by prop through 59 / 52 / 64 / 42 / 38 component files, six levels deep.**
One chain, verified: `App` → `AppContent` → `ClientProfileView` → `ClientInfoSheet` (`ClientInfoSheet.tsx:327`) → `ClientDossier` (`:334,694,722`) → `ClientJournalTab` (`:89`) → `ClientCheckInPanel` (`:306`, as `trainer`). `ClientJournalTab.tsx:122` then falls back to `auth.currentUser?.uid` anyway, because the two ids differ. **27. High — the 140 kB Academy seed and every admin tool ship in every trainer's entry chunk.**

**28. Medium — no `build.target`, and the studios run iPadOS 15/16.**
`vite.config.ts` sets no `build.target`; Vite 8's default is `baseline-widely-available` = `safari16.4` / `ios16.4` (`node_modules/vite/dist/node/chunks/node.js:699–705`). `docs/ops/TESTING-CHECKLIST.md:162,182,535,650` tests "Old iPad (iPadOS 15/16) cold load … a regex the old Safari can't parse would blank the whole app", and KNOWN-TRAPS bans regex lookbehind by convention. **Why it matters:** the convention covers regexes only; esbuild will leave any 16.4-era syntax (class static blocks, `#x in obj`, etc.) untranspiled, and a dependency bump can blank a 15.x iPad with no test catching it. **Direction:** `build.target: ["safari15", "ios15"]` (or the oldest iPad on a floor) and a CI check that the built entry parses under that target.

**29. Medium — the stylesheet blocks on Google Fonts, downloads a font nothing uses, and the login screen fetches a texture from a third-party site.**
`src/index.css:1` `@import url('https://fonts.googleapis.com/…Saira+Condensed…&family=Inter:wght@400;500;600;700…')` — `Inter` appears nowhere else in `src/`; `Geist` is already self-hosted via `@fontsource-variable/geist`. `LoginScreen.tsx:31` loads `https://www.transparenttextures.com/patterns/hexellence.png`. **Why it matters:** the app claims offline persistence, and a captive or slow studio Wi-Fi stalls the whole stylesheet on googleapis; Saira Condensed is the brand display face and falls back silently. **Direction:** self-host Saira, drop Inter, delete the texture.

**30. Medium — offline is invisible, and writes queued offline can be lost by a sign-out.**
`firebase.ts:25–29` enables persistence (single-tab, deliberately), but no code reads `navigator.onLine`, a snapshot's `fromCache`/`hasPendingWrites`, or shows any offline state (`grep` finds none outside the Mindbody link mode). A trainer who finishes a session on a dropped connection sees "Finish session" succeed; the write sits in IndexedDB. Pending writes are replayed with the credentials the SDK has when it reconnects, so a "Log Out Facility" tap (`AppContent.tsx:1486`) before the network returns is a plausible way to lose a session silently — worth confirming on a real iPad. Two iPads are not a problem (each is its own browser); two *tabs* on one iPad fall back to memory cache as the comment says. **Direction:** an "offline — saving on this iPad" mark in the session bar, and refuse (or warn on) sign-out while `hasPendingWrites`.

## 4. Direct, challenging questions for AJ

**Routing and state**
1. Sixteen views, four ad-hoc "intent" mechanisms (`learningJump`, `requestPlanner`, `section-memory`, the profile's `sessionStorage` handoff), a bell that opens clients, and `setCurrentView` called from 39 places: is "no router" still a decision, or is it an accident you keep paying for? What would break if `currentView` became a URL (`/studio/solon/client/123/journey`) tomorrow — deep links from notifications, a refresh that lands back in the session, the iPad back-swipe?
2. After a Safari refresh mid-set the app opens on the Hub and the session is one tap away. Given "act as pen and paper in terms of reliability", why isn't a remembered In-Progress session resumed *automatically*?
3. `appMode` is a second axis that only the header menu sets, so Settings' "Open Operations" and the bell leave the trainer bar under an Operations screen. Should the mode be derived from the view (a view *is* trainer or operations), and the toggle go?

**Streams and cost**
4. The shell streams ~300 full `Client` documents to every iPad at the largest studio and re-pushes each one on every completed session and every nightly job. Which screen actually needs the full document for *every* client, as opposed to a name, a home studio and the renewal line? If none, is a roster projection (or an "active clients only" filter before the FileMaker import) worth doing before the next studio comes on?
5. Should the unit of an app-wide stream be the studio (today) or the screen? `trainers`, `studios`, `networks`, `machines` and `hub_announcements` are whole-collection listeners for every trainer; the Overview already opens its own week, the profile its own seven journal streams. Would you rather the shell owned *nothing* but the studio and the signed-in trainer?
6. `hub_announcements` is read whole (every studio's, forever, no expiry filter) and every reader stamps every document. Is an announcement a document each iPad watches, or a thing the nightly job could fold into a per-studio "notices" document?

**Admin tools in the shell**
7. The wipe, the catalog re-seed, the trainer reorder and the New Clients dialog live in `AppContent` and in every trainer's first download. Should the shell own *any* admin tool, or should everything an administrator does that touches more than one studio live in `scripts/` behind the service account, with the app only ever able to write one document at a time?
8. The `?view=trainer-hub` impersonation and the `jurgensaj@gmail.com` bootstrap are both still in the shipped bundle. Are they in use? If not, can they go before the next deploy?

**Identity and roles**
9. `lib/permissions.ts` has a 170-line `hasPermission` nobody calls, and "is this an Admin" is spelled out inline six ways (with and without `Overseer`). Which is the answer: the token's role, the document's role, or both — and who is `Overseer` today?
10. "Switch Trainer" dead-ends on the access-request form. Trainer PINs are gone; is there any world where two trainers share one signed-in iPad, or is that menu item (and `max_strength_trainer_id`) simply a leftover to delete?

**Theme and the floor**
11. The post-session screen is dark "whatever the theme"; the tracker is not, and its header carries the theme toggle. Is the floor meant to be one theme (dark, glanceable at arm's length, no light-mode contrast bugs) with light mode only for off-floor screens — and if so, should the toggle leave the tracker's header?
12. A studio's `brandColor` recolours the CTA on every screen. Given "Max Strength owns the method; a studio owns its hardware", does a franchisee own the app's orange?

**Reliability**
13. The app claims offline persistence but never shows offline. What should a trainer see at Finish when the iPad has no Wi-Fi — and is "Log Out Facility" allowed while writes are still pending?
14. One error boundary wraps the whole shell, so any render error anywhere replaces the Active Session with "Something went wrong · Reload". Is that acceptable on Rank 1, or should every routed view fail alone with the nav still there?
