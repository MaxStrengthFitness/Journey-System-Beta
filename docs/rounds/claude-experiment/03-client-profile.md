## 1. What this area does — my interpretation

**The Hub is a schedule, not a client list.** `src/components/ClientsView.tsx` draws today's Mindbody bookings as a table of trainer columns × 30-minute rows (5:30 AM–8:00 PM, stretched to fit), from the app-wide `schedules` prop, with a "Now" line and a seven-day carousel. Each booking is a `ScheduleBlock` (`src/components/schedule/ScheduleBlock.tsx`) that resolves *strictly* to `clients/{mindbodyClientId}` (no name matching) and shows a name, a time, up to two marker chips from `src/lib/hub-markers.ts` (consultation, first session, milestone, birthday, back after a break, away, medical, renewal due) and three flags from `src/lib/client-alerts.ts` (a red priority triangle, a Pulse red flag, a clinical dot). Tapping a block opens the profile; there is no Start affordance on the block, so the shortest path from the Hub to an Active Session is block → profile → Start session → START on the briefing (three taps). Typing in the header search replaces the timeline with a second, older "Client Directory" list of cards (`:1344-1513`) that *does* have a Start button; a separate full screen, `src/components/ClientDirectoryView.tsx`, is the directory reached from the bottom bar when no client is selected, with its own copy of the same prefix-search query. The Hub also still contains a 360-line "Edit Client Profile" form that nothing can open (§2, H6).

**The profile is four tabs, each a question.** `src/components/ClientProfileView.tsx` (1,863 lines) is the shell: it owns every per-client Firestore read and write, the header (`features/client-profile/ProfileHeader.tsx` — name, four fact tiles, Kaizen toggle, Note, Sync, and the hero Start Session / In-progress dropdown), a progress-report banner above the header, and a Base UI `Tabs` with four panels from `PROFILE_TABS` (`features/client-profile/profile-nav.ts:78-83`), in this order: **Journey** (the sessions × machines grid, `features/journey-grid/RecentJourneyView`, 50 sessions a page), **Programming** (`ProgrammingTab.tsx`: Routine A · Routine B · All Machines · Setup on the 48px `ProfileSubnav`), **Notes & Profile** (`ClientInfoSheet` inline → `client-dossier/ClientDossier.tsx`, one scrolling spine of eight sections: Notes · Who they are · Life (FORD) · Body · Goals · Focus · Pulse · Admin, with a sticky Save bar for the record's fields) and **Activity Archive** (`ClinicalHistoryTab.tsx`: Calendar · Sessions · Deep Dive · Reports). Where the trainer is is a `ProfileLocation` reducer (`useProfileNav`), resumed only from a one-shot handoff; a client always opens on Journey. ARCHITECTURE §2.3 still says seven tabs, "paged 15", and that the profile streams `sessionNotes` and `trainerFocuses` and carries two hidden dead panes — all five claims are stale on today's master: four tabs, 50 a page, the legacy collections are read only by the journal hook on the record tab, and the dead panes were deleted (comment at `ClientProfileView.tsx:1655-1659`).

**Notes are one collection with nine tributaries.** `src/hooks/useClientJournal.ts` (1,153 lines) opens **seven live listeners** per mount — `journalEntries` (300, ordered), `clientFocuses`, `focusRecords`, `sessionNotes`, `clinicalIncidents`, `trainerFocuses` (200 each, unordered guard rail) and `sessions` (40, for `sessions.notes`) — and merges them with three in-memory adapters over the client document (`client.events`, seven profile text fields, the Mindbody notes) into one `JournalEntry[]` and one `ClientFocus[]`. It is mounted by the dossier (once, shared by three sections), the tracker, the briefing and the standalone journal tab. Writes go through `createJournalEntry` from the composer (`components/journal/JournalComposer.tsx`: category chips → text → Loudness → mattering window → save), the header's Quick Note (`features/client-notes/QuickNoteDialog.tsx`), the in-session sheet, the closing note and the machine-note mutation. `features/client-notes/mattering.ts` is the one rule for "does this note matter today". FORD details live in `clients/{id}/ford` (`features/ford/`), deliberately outside the journal because `journalEntries` is readable by any signed-in user.

**Pulse is a chain of draft reports.** The living assessment (`features/subjective-report/`) is stored as a `progressReports` document with `isCheckInOnly: true` and `status: "Draft"` that autosaves (`useCheckInDraft.ts`, `checkin-draft.ts`); "Save this round" flips it to Finalized, stamps `client.subjectiveSnapshot` (what the Hub's Pulse flag reads) and the next edit starts a fresh draft whose "from" values are reconstructed from the history at read time (`assessment-history.ts` — the "living rule"). The `clients/{id}/checkIn/current` + `checkInSnapshots` shape decided in ARCHITECTURE §3.8 was not built; the draft *is* the living record. The Client Progress Report (`src/components/ClientProgressReportView.tsx`, 2,387 lines) is a five-step editor over one big `report` state object that reads every completed session and every exercise log of the client once (`lib/progress-utils.ts`), drafts three data-backed accolades (`features/progress-report/accolades.ts`), shows the Pulse read-only, and prints. The Deep Dive (`features/clinical-review/`) generates on request over a date range and is pure after the read.

**History is its own read.** Activity Archive → Calendar/Sessions is one mount of `features/client-history/ClientHistoryTab`, with `useSessionHistory` (a 200-session live listener, 2,000 on "Load full history") and per-month set loading; the session dialog (`SessionDetailDialog.tsx`) edits sets, adds/removes machines, edits `sessions.notes`, stamps the edit, and deletes with a batch and the counter unwind. "Log past session" backfills a session that counts.

## 2. Anomalies — the irregular, clunky and suboptimal

### Critical

**C1. The Hub's red flag cannot see a critical note written in Journey.**
`src/components/schedule/ScheduleBlock.tsx:94-102` → `src/lib/client-alerts.ts:75-80` derives `hasPriorityNote` from `client.priorityNote`, `client.hasPriorityNote` and a High-priority `client.events[]` entry. Nothing in `src/`, `functions/src/`, `scripts/` or `server/` writes any of those three (only `src/types.ts:735-737` declares them), and no Hub-side path reads `journalEntries` (`useStudioRoster`, `useLiveSchedule`, `AppContent`, `hub-markers.ts` — none). Yet `src/types/journal.ts:426` tells the trainer a Critical note is "Pinned, on the briefing, and marks the Hub card", and `docs/rounds/2026-09-16-reporting-round.md:58` records that as the decision.
*Why it matters:* the-floor.md's "Red flags: a small marker at the top" is unmet on the one screen a trainer opens to run the day; the UI copy promises something the data path cannot do.
*Direction:* either a small cache on the client written by the journal (`criticalNoteCount`, like `fordSummary`) or one studio-day read of `journalEntries where studioId == … importance == critical` (the index exists since the Operations round) feeding `hubMarkers`.

**C2. `client.priorHistory` has exactly one writer in the repo and it is unreachable.**
`ClientProfileView.tsx:194` `isEditingSessionCount` becomes true only through `openSessionCountEditor(true)` (`:497-505`), which is wired only to the dialog's own `onOpenChange` (`:1748`) — a dialog cannot open itself. `ProfileHeader.tsx:563-598`: the Completed-sessions tile's `onClick` is `renewal?.onOpen`; no `onEditCount` prop exists. `src/lib/prior-history.ts:117` `recordImportedSessions` has zero callers. `src/features/admin/data/AdminDataReportsTab.tsx:176` tells administrators the pre-Journey history "is **Sessions before Journey** on their profile".
*Why it matters:* "Prior history is real history" (CLAUDE.md) has no UI; every long-standing client reads as a Journey-only client and the header's "412 before Journey" line can never appear.
*Direction:* one door — the tile itself, or the Admin section of the record — and delete the orphan if the answer is "scripts only".

**C3. A trainer can never discard a Pulse draft, and never delete a report, but both buttons are offered.**
`features/subjective-report/checkin-draft.ts:230-232` `discardCheckInDraft` is a `deleteDoc` on `progressReports/{id}`; `firestore.rules:1611` `allow delete: if isSuperAdmin() || isFranchiseOwner()`; `components/journal/ClientCheckInPanel.tsx:540-541` shows "Discard draft" to every trainer (`useCheckInDraft.ts:444-461` swallows the refusal into a toast). The archive's Delete (`components/journal/ProgressReportArchive.tsx:121-125`, hover-revealed) → `ClientProfileView.tsx:179-189` `performReportDelete` is refused for the same roles *after* the trainer has typed "DELETE REPORT" into `StrongConfirmationModal` (`:1853-1860`).
*Why it matters:* the same bug class the history round fixed on Sep 17 ("the Delete Session button had never worked for anyone who would press it"); a Pulse draft with wrong answers is stuck for a Life Transformer or Studio Leader. For an admin the archive's delete *does* work on the open Pulse draft — deleting the living record and its change log in one hover-tap.
*Direction:* a rules change for a trainer's own draft, or an in-app "discard" that empties the draft rather than deleting the document; hide the archive delete for roles the rule refuses.

### High

**H1. A top-level tab tap unmounts everything, so drafts, edits and the generated report die — and every return re-fetches.**
`src/components/ui/tabs.tsx` wraps Base UI `Tabs.Panel`, whose default is `keepMounted = false` (`node_modules/@base-ui/react/tabs/panel/TabsPanel.js:37`); no `keepMounted`/`forceMount` anywhere in `src/`. Consequences, each verified: (a) the record's unsaved edits (`ClientInfoSheet.tsx:100-101` `formData`/`dirtyFields`, no storage) are lost when the trainer glances at Journey; (b) Setup's unsaved drafts (`features/machine-fit/ui/SetupView.tsx:152` `useReducer`) are lost, although `ProgrammingTab.tsx:37-40` promises "a trainer half way down a FileMaker chart who glances at Routine A must find the chart where they left it" — a glance at *Journey* is the likelier glance; (c) the generated Deep Dive (`features/clinical-review/useClinicalReport.ts:72` `useRef` cache) is lost, although `ClinicalHistoryTab.tsx:40-44` says "once generated it stays mounted"; (d) the fifteen listeners of Notes & Profile are torn down and re-created per visit; (e) `ClientProfileView.tsx:770-837` re-runs the 50-session query plus five `exerciseLogs in` chunks on every return to Journey or the Archive (`:837` deps include `activeTab`).
*Why it matters:* on a held iPad a tab tap is a reflex; silent loss of typed medical history is the worst kind of "FileMaker taught them to hate" behaviour, and "switching a sub-view must cost no fetch" stops one level too low.
*Direction:* keep the four panels mounted (`keepMounted`, hidden) or lift the record's draft to the profile shell / sessionStorage the way the session-note draft was lifted in the fluidity round.

**H2. A late client's flags vanish the minute the booking's start time passes.**
`ScheduleBlock.tsx:77-82` `isCompleted = … getMillis(startTime) < Date.now()`; `:101` `showFlags = !isCompleted && !isUnavailable`; `:118` markers are `[]` when completed; `:157-158` the surface greys to `opacity-70`.
*Why it matters:* at 9:01 for a 9:00 booking whose client is walking in, the priority triangle, the Pulse red flag, the clinical dot and every marker are removed from the card — exactly the moment the trainer looks. "Completed" should come from the live session (`workoutSession?.status`) or the booking's `status`, never the clock.
*Direction:* treat past-start-and-no-session as "due", keep flags until a session is Completed or the day is over.

**H3. The progress report prints fabricated clinical claims when a field is blank.**
`ClientProgressReportView.tsx:1559-1560` prints "Incredible work this quarter. Your neurological adaptations are now clearly visible in the data. Your force output is reaching peak clinical efficiency." whenever `trainerNotes` is empty; `:1190-1191` "Your dedication to this clinical protocol is exactly what drives meaningful biological change."; `:684` seeds the narrative; `:279-283` stores a canned "The Next 6 Months: We will transition to Routine B, increasing time-under-tension by 10% to fortify your lumbar spine…" on every new report's `strategy`.
*Why it matters:* "Sentences, not scores — every claim has a named minimum sample" and "a confident wrong number is worse than a missing one" are the two product rules this violates, on the one artefact a client takes home. The accolades in the same file do it right (nothing empty prints).
*Direction:* blank prints nothing; delete the `strategy` default.

**H4. Unbounded per-client reads that the FileMaker import will multiply.**
`src/lib/progress-utils.ts:41-56` reads every Completed session *and every exercise log* of the client with no limit on every report open; `features/client-profile/useTopTrainer.ts:54` reads every session (no limit) for a client with no tally, then writes the client (`:58-64`); `features/clinical-review/useClinicalReport.ts:130` reads all `clinicalIncidents` for the client; `ClientProfileView.tsx:575-578` subscribes to `routineAdjustments where clientId ==` with no limit (the journal hook's collections got a 200 guard rail in the cost round; this one did not).
*Why it matters:* a 300-session client is ~2,700 documents per report open today; the import makes that every long-standing client.
*Direction:* bounded windows (the report already has a start date), and a `limit` on the adjustments stream.
