## 1. What this area does — my interpretation

**The method and the hardware.** Max Strength's product is the METHOD (musculature, cadence, both turnarounds, the handoff, the cues); a studio owns the UNIT in its room (name, baseline positions, body-type adjustments, the dials and their defaults, starting load, a photo). The code that says this is `src/lib/machine-template.ts` (`STUDIO_DEFINITION_FIELDS`, `tierOf`, `scopeOverrides`) and `src/lib/resolve-machine.ts` (the merge: additive safety arrays union, `universalBaseline` / `bodyTypeAdjustments` / `defaultSettings` merge per key, everything else replaces). The data model is three Firestore layers — `machines/{m-*}` (`MachineCatalogEntry`, admin-write), `studios/{s}/roster/{machineId}` (`RosterEntryFromCatalog` with `overrides`, or `RosterEntryCustom` with a whole `definition` and `basedOn` lineage), and `clientMachineSettings/{clientId}_{machineId}` (the client's values, `sources`, `fitAcks`, weights, notes). `useStudioMachines(studioId)` collapses layers 1+2 into `ResolvedMachine[]` (`src/hooks/useStudioMachines.ts`, on top of `useMachineCatalog`). The twenty standard machines are GENERATED into `src/data/machine-definitions.ts` (140 KB, Academy prose verbatim) by `scripts/generate-machine-definitions.ts`, which joins the four `standardized-setup-guide-batch*.md` files with three older in-repo data files: `machine-anatomy-map.ts` (diagram targets + movement pattern), `machine-database.ts` (the older cue lists, keyed `leg_press`), and `default-machines.ts` (the LEGACY `Machine` shape keyed `m-leg-press`, with `settingOptions: ["Gap","Seat Angle",…]`). "Restore standard machines" (`AppContent.tsx:1005`) writes the generated list to `machines/*` with `merge: true`, so the legacy keys stay on the same documents.

**How a machine reaches the floor today.** This is the part that decides everything else: the Active Session, the client profile (Journey grid, Equipment tab, Routines, Setup) and the routine builder all receive `machines: Machine[]` — the LEGACY shape — from `AppContent.tsx:481` `useMachines(isDataReady, DEFAULT_MACHINES)`, which streams the whole `machines` collection ordered by the legacy `order` field and merges it with the code defaults by id. The tracker (`WorkoutTrackerView.tsx:247`) and the profile (`ClientProfileView.tsx:257`) also call `useStudioMachines(activeStudioId)`, but use it for ONE thing: `studioFloorById[id]?.order` (tracker `:2028`, profile `:925`). The dials the Now Bar shows come from the legacy `machine.settingOptions` / `machine.standardSettings` run through `orderMachineSettings()` in `src/lib/utils.ts:241` (tracker `:2050-2054`), never from `settingFields` / `defaultSettings` / a roster override. Only the Learning → Catalog page (`features/catalog/useCatalogMachines.ts`) and the studio-management screens (`StudioInventoryManager`, `MachinesSection`, Relay's floor pieces) read the roster as the floor. So ARCHITECTURE §3.5's row "Sessions still use the app-wide machine list" is still true on today's master, and it is truer than it says: the roster's dials, names, defaults and custom machines reach the Catalog page and nothing a trainer holds during a session.

**Per-client settings and the three writers.** `clientMachineSettings.settings` is a `Record<string,string>` whose KEYS are whatever the writer used: the legacy label (`"Back Pad"`) from the Equipment tab / MachineSheet (`features/equipment/adapters.ts:153-173` builds the field list from legacy `settingOptions` first so keys keep matching), the catalog slug (`"back-pad"`) for catalog-only fields, or whatever `parseMachineSettings` produced on a FileMaker import. Three UIs write the document with three contracts: `features/equipment/mutations.ts:saveSettings` (`mergeFields`, `sources`, `settingHistory` row, journal entry, fit-index upsert), `features/machine-fit/setup-save.ts` (batch, same fields), and the full-screen chart `components/WorkoutChartGrid.tsx:233-244` (bare `setDoc merge:true`, `updatedBy: email`, no history, no journal, no sources). Session completion (`lib/sync-utils.ts:315-335`) rewrites `currentWeight`. The audit trail is filed under the MACHINE (`machines/{id}/settingHistory`, `mutations.ts:122`), and the rules leave that subcollection open to any signed-in user for every operation (`firestore.rules:1355-1357`).

**Studio-level "standard settings" live in three places.** (a) the roster entry's `overrides.defaultSettings` written by `StudioMachineEditor` (canonical per the README); (b) the legacy collection `studioMachineSettings/{s}_{m}` written by `features/catalog/StudioSetupCard.tsx:116-127` — mounted on the Catalog page AND as "this studio's standard settings" in My Studio → Machines' door (`MachinesSection.tsx:104, 371`), read back only by those two cards, and by nothing on the floor; (c) `Studio.machineSettings` (`types.ts:1763`), read by six fallback chains (`ClientProfileView.tsx:942`, `WorkoutChartGrid.tsx:563`, `PerformanceEntryDialog.tsx:185`, `useFitFloor.ts:40`, `equipment/adapters.ts:386`, `MachineSettingsDashboardModal.tsx:52`) and written by nothing in the repo.

**The editor, fit, trends, Academy, routines.** The machine editor is a full screen (`features/admin/machines/editor/MachineEditor.tsx` + `sections.tsx` + `controls.tsx`), eight sections, ~55 inputs, read-only "method" sections for a studio; `completeness.ts` names gaps in English. Machine fit (`features/machine-fit/`) is a cohort engine (tolerance ladder, clusters, passive audit, k-anonymous company tier at `CELL_MIN_CLIENTS = 5`) reached from Programming → Setup and Operations → Machine fit. Separately, the Equipment tab / MachineSheet offer a height-band suggestion from the weekly `machineTrends` document (`features/equipment/setting-suggestions.ts`) — a second, unrelated suggestion engine. The Academy is ~1.4 MB of generated JSON, code-split per module by `useAcademyContent.ts` (only the 16 KB index is static). Routines are two `routines/{id}` documents per client identified by `name === "Routine A" | "Routine B"`; templates are `routinePresets` (company / studio / trainer tiers); "Use today" writes `clients/{id}.preferredTodayRoutineId` — a persistent preference, not a day.

### Answers to the eight questions the task set

1. **Inventory of "what is a machine".** Six stored/seed shapes: legacy `Machine` (`types.ts:945`, 36 optional fields, `settingOptions` labels, `standardSettings`, `targetMuscles` string-or-array), `MachineKnowledge` (`machine-database.ts:8`, cue lists, keyed `leg_press`), `MachineAnatomyMap` (`machine-anatomy-map.ts:36`), `MachineDefinition`/`MachineCatalogEntry` (`types/machines.ts:392, 466`, 26 top-level fields, ~55 leaves), `StudioMachineRosterEntry` (two variants), `StudioMachineSetting` (legacy, `types.ts:1074`), plus `ClientMachineSetting` for the client layer. Then six view shapes on top: `ResolvedMachine`, `CatalogMachine` (`catalog/types.ts`), `EquipmentMachine` (`equipment/types.ts:118`), `JourneyMachine` (`journey-grid/types.ts:51`), `PickerMachine`, two different `FloorMachine`s. **Duplicated:** name (all six), region/pattern (Machine.anatomicalRegion, anatomy map, definition), muscles (`targetMuscles` string, `targetMusculature[]`, `primaryMuscles: MuscleId[]`, `musculature.primary: string[]` — four spellings), cues (`setupCues`/`executionCues` in the database vs `universalBaseline`/`execution.keyCues` in the definition), dials (`settingOptions: string[]` vs `settingFields: MachineSettingField[]`), defaults (`standardSettings` vs `defaultSettings`), handoff (`Machine.requiresHandoff`, `MachineKnowledge.requiresHandoff`, `execution.requiresHandoff`), warnings (database vs definition). **A new franchise machine** (custom) is written ONCE in `studios/{s}/roster/{sm-*}.definition` — but to be usable on the floor it also needs a `machines/{id}` document with a legacy `order` field (because the tracker reads the global list, and `useMachines` drops documents without `order`), an entry in `MACHINE_ANATOMY` (routine engine), `MACHINE_ABBR` (every code/abbreviation on screen), `MACHINE_CATEGORY`/`MACHINE_FAMILY` (sequencing rules), `DEFAULT_MACHINE_DISPLAY_ORDER` (fallback order), and a name that survives four substring classifiers (`getMachineStyle`, `movementGroupFor`, `regionOf`, `isSidesMachine`). In practice: seven places, four of them source code.

2. **The settings vocabulary.** The catalog knows 14 dial keys (`gap` ×20, `seat` ×13, `back-pad` ×8, `handles` ×5, `chest-pad` ×2, `thigh-pads`, `shoulder-pads`, `seat-pad`, `seat-distance`, `seat-angle`, `back-pad-height`, `back-pad-angle`, `arms`, `ankle-pad`), all `type: "text"`, zero `options`, zero `shortName` (grep of `machine-definitions.ts`). The floor's shorthand is decided by `orderMachineSettings` (`lib/utils.ts:248-258, 379-385`): six recognised names (seat/gap/back pad/chest pad/handles/arm pad), everything else shortened to its first letter. FileMaker's letters map as: S→Seat ✓, G→Gap ✓, B→Back Pad ✓ (but "Blocks" also → "B"), H→Handles ✓, E→"E", Ft→"F", Pad/Pads→"P", and "Seat Angle"/"Seat Distance"/"Shoulder Pads" all → "S". Values are free text so `1.5`, `N`, `W`, `M`, `SH` store fine; `"-"` stores as a chip `G -` on the floor **[probe]** but `normalizeSettingValue("-")` returns `null` for trends/fit (`machine-trends/trends.ts:156`), so "G-" counts as "no gap recorded", not "gap none". **Two leg presses from two vendors:** the model can hold it — a second unit must be a `custom` roster entry `sm-{studio}-leg-press-hoist` with `basedOn: "m-leg-press"` and its own `settingFields` (`types/machines.ts:555-574`); `comparisonKey` rolls it up with every leg press (`resolve-machine.ts:328`). But the tracker cannot show it (global list), the routine engine treats it as `unmapped` (`routine-builder/engine.ts:88` reads `MACHINE_ANATOMY[id]`, `canonicalMachineId` returns `sm-*` unchanged, `basedOn` is never consulted), and its dial labels never reach the Now Bar. So: representable in the roster, unreachable on the floor. "G-" on a leg press lands in `clientMachineSettings.settings["Gap"] = "-"` if typed on the Equipment tab / MachineSheet (key = legacy label because `buildFields` keeps legacy keys), or `settings["gap"]` if saved from Programming → Setup (normalised key), and the two spellings then render as two chips **[probe]**.

3. **The four hooks.** `useMachines` (`hooks/useMachines.ts`, 1 caller: `AppContent.tsx:481`) returns legacy `Machine[]` from `machines` ordered by `order`, merged with `DEFAULT_MACHINES`; every screen gets it as a prop (10 `machines={machines}` in AppContent). `useMachineCatalog` (12 direct callers + inside `useStudioMachines`) returns raw `MachineCatalogEntry[]` and an unmemoised `byId`. `useStudioMachines` (14 callers) resolves catalog + roster; the tracker and profile use it only for order. `useCatalogMachines` (3 callers: Catalog page, Learning home, Learning search) adapts to `CatalogMachine`. **Verified:** the tracker's rows (`WorkoutTrackerView.tsx:2022-2054`), its "+" add-machine (`:2375-2378` over the grid's rows), the routine builder's picker (`EditRoutineDrawer.tsx:768` passes the prop; `RoutineBuilder.tsx:117-124` builds `pickerMachines` from it) and the Equipment tab all read the GLOBAL list. §3.5 is still true. `src/features/README.md:77` says `useStudioMachines` is for "the tracker's settings" — it is not.

4. **The editor as a screen.** `SECTIONS` in `completeness.ts:47-118` cover 26 top-level fields; with the nested objects that is roughly 55 inputs plus per-item arrays. A studio may write `STUDIO_DEFINITION_FIELDS` (9: name, shortName, universalBaseline, bodyTypeAdjustments, settingFields, defaultSettings, baselineLoad, imageUrl, formVideoUrl) plus the four additive safety arrays; 13 method fields are locked. Enforcement is app-side only: `scopeOverrides` at `MachineEditor.tsx:117` and `StudioMachineEditor.tsx:137`; `firestore.rules:1849-1857` checks WHO writes a roster entry (`isStudioOwnerOrHeadTrainer`) and `rosterWriteValid` (sharing/`studioId`), nothing about the contents of `overrides` — `machine-template.ts:153-156` says so. The round doc's "For AJ #4" already lists this as not built.

5. **Machine fit.** `CELL_MIN_CLIENTS = 5` (`fit-index.ts:237`), `MIN_CLIENTS = 5` (trends), `UNIVERSAL_MIN_CLIENTS = 10`, `LINK_MIN_CLIENTS = 10`. Cohort: `buildCohort` widens every switched-on numeric factor one ring at a time (`cohort.ts:103-112`) until `spec.minClients`, excludes the client herself, keeps the widest ring as a second opinion. On Programming → Setup a trainer sees one row per machine with Check / Set up / Quick entry modes, suggestions with Use, "Accept strong", a FileMaker shorthand box. **Reachability from the floor:** none. Nothing under `features/journey-grid`, `WorkoutTrackerView`, `briefing` or the MachineSheet imports the fit engine (grep); `SetupView` is mounted only by `ProgrammingTab.tsx:361`. What a trainer at a machine with a first-timer gets is `SetupPromptDialog` → `SettingsCard` → `suggestFromTrend` (the OTHER engine, company-wide `machineTrends` height band ±2", no studio tier, no clusters).

6. **The Academy.** `du -sh src/features/academy/content` = **1.4 MB** (overviews 246 KB, mastery 160 KB, summary 156 KB, cards 108 KB…). Chunking is right: `useAcademyContent.ts:37-51` dynamic-imports one JSON per module; the build shows separate chunks (`overviews` 237 KB, `mastery` 152 KB, `summary` 148 KB, `cards` 103 KB, `learning` 80 KB) and only the 16 KB index is static. The Learning tab itself is lazy (`AppContent.tsx:193`). So the Academy costs a floor iPad nothing until opened. What DOES sit in the initial 372 KB `index` chunk is `machine-definitions.ts` (140 KB of source), imported statically by `AppContent.tsx:226` for the admin-only "Restore standard machines" button — the Academy prose ships to every trainer on every load to serve one button; the 63 KB legacy `machine-database` is its own chunk.

7. **Routines.** A/B = two `routines` documents per client found by `name` string (`routine-rows.ts:66-76`, `EditRoutineDrawer.tsx:149-163`, tracker `:737` sorts by name so A is first); B is switched on via `clients.isRoutineBActive` and requires a typed reason ≥3 chars (`ClientProfileView.tsx:625`). A template (`RoutinePreset`) becomes a routine by `applyPreset` copying `machineIds` (filtered to what the studio has) and recording `templateId/templateName/templateMachineIds/templateAppliedAt` (`Routine`, `types.ts:1007-1016`); drift is computed later against the snapshot. "Use today" (`ClientProfileView.tsx:683-723`) writes `clients/{id}.preferredTodayRoutineId` and patches the in-progress session's `routineId`; it persists across days. Versus FileMaker: **Set As Template** ≈ "Save as studio preset" in the drawer (`EditRoutineDrawer.tsx:394-419`, tier `trainer`), **Use Template** ≈ apply preset, **Copy This Session** has no equivalent — today's session order is deliberately never written back to a routine (the-floor.md, "routines stay profile-only"), and there is no "make today's order the routine" action.

8. **Copy on screen.** Raw hex: `components/anatomy/BodyModel.tsx:68-69` (`#0A548B`, `#6FB4E4`, `#4B555C` defaults); `catalog.css:83` `color: #fff`. Truncation: `StudioInventoryManager.tsx:95` (machine NAME in reorder mode), `:548` (pattern line), `EditRoutineDrawer.tsx:866, :885` (`truncate max-w-32` on preset names). Naming: catalog names are ALL CAPS and studio slang (`BICEP`, `LUMBAR`, `CX (4 WAY NECK)`, `CHEST/PEC FLY`, `machine-definitions.ts:1011, 1838, 1964, 899`) while the Academy, `MACHINE_DATABASE` (`Biceps Curl`? no — `Seated Leg Curl`, `Cervical Extension`) and `MACHINE_ABBR` (`Cx`, `Lumb`, `Flye`) each spell them differently; `shortName` exists on the type and editor (`sections.tsx:81-88`) and has **no reader** anywhere (grep) — every code on screen comes from the static `MACHINE_ABBR` table (`academy.ts:125-146`), so a custom machine has no code.

## 2. Anomalies — the irregular, clunky and suboptimal

1. **Critical — `src/components/WorkoutTrackerView.tsx:2072-2082` — the Now Bar and grid collapse a machine's dials onto their first letter and drop the collisions.** `orderMachineSettings` returns `[shortKey, value, fullName]` and the tracker builds `settings: Object.fromEntries(entries.map(([k, v]) => [k, v]))` keyed by the ONE-LETTER key. On the Leg Press (legacy options `Gap, Seat Angle, Shoulder Pads, Seat Distance`, `default-machines.ts:243`) three dials shorten to "S" and only the last survives: a client saved at Seat Angle P2 · Seat Distance 7 · Shoulder Pads 3 reads on the Now Bar as **"Gap 2 · Shoulder Pads 3"** **[probe]**. The Seated Dip loses one of its two back-pad dials the same way. Why it matters: the Now Bar is the "which machine → its settings" glance the-floor.md defines, and on the most-used machine it silently loses the seat position. Direction: key the rail by the field's real key and derive the display letter separately; never use the abbreviation as a map key.

2. **Critical — `src/lib/utils.ts:342-362` — "Gap" is invented for every machine and every client.** With no gap on file the function writes `mergedSettings["Gap"] = "0"`, so a client with NO settings at all renders `G 0` on the Now Bar, the grid rail and the Equipment rail (`MachineRail.tsx:30` passes only `machine.settings`) **[probe: `orderMachineSettings({})` → `[["G","0","Gap"]]`]**. The generated catalog says the Academy's starting gap is 2 on the row, pulldown, pullover, press, flye, 1 on three others, 5 and 4 on two more, and per-client on the leg press (`machine-definitions.ts:151, 512, 641…`). A confident wrong number on the screen looked at twice per machine. It also makes `JourneyGrid.tsx:490` ("No machine settings saved for this client.") unreachable. Direction: show nothing when nothing is saved; a studio default is a ghost, never a value.

3. **Critical — `src/features/equipment/adapters.ts:65-67` — `ABSOLUTE_STANDARDS = { gap: "0" }` pre-fills Gap 0 "for real" on every first set-up.** `SettingsCard.tsx:45-47` seeds the draft with it and it is saved as a typed value. Same contradiction with the catalog's gap defaults as above, but this one is WRITTEN into `clientMachineSettings` and then counted by machine trends and machine fit as evidence ("most clients here use gap 0"). Direction: delete the constant; use the resolved machine's `defaultSettings` as a ghost.

4. **Critical — `src/hooks/useMachines.ts:14` + `src/features/admin/machines/CatalogMachineEditor.tsx:72-92` — a machine created in the new catalog editor never reaches the floor.** The editor writes `defaultOrder` and no legacy `order`; `useMachines` queries `orderBy("order")`, and Firestore drops documents missing the field (the trap `useMachineCatalog.ts:12-15` names for itself). The generated seed also has zero `order` keys (grep), so on a fresh database the tracker would show only the code defaults. Direction: one reader of the catalog, ordered client-side.

5. **Critical — the floor never reads the roster (already known, §3.5 — still true and wider than stated).** `WorkoutTrackerView.tsx:2050-2054` reads `machine.standardSettings` / `machine.settingOptions` (legacy, global); `EquipmentTab.tsx:68` / `MachineSheet.tsx:104` / `SetupPromptDialog.tsx:62` adapt the legacy prop; `RoutineBuilder.tsx:117-124` picks from it. So: a studio's dial labels edited in "Set up for us" (`StudioMachineEditor`), a custom machine, "We don't have this", and a corrected catalog `settingFields` all change the Catalog page and nothing else. `StudioInventoryManager.tsx:408-409` tells the leader "Trainers running a session here see exactly this list" and `:483-484` "This is the sequence used by … the Active Session" — the first is false, the second is true only for order. Direction: finish the migration in the tracker and the profile first (they are the readers that matter), then delete `useMachines`.

6. **High — `src/features/equipment/adapters.ts:193, 381` — the Equipment tab looks up `MACHINE_DATABASE[machine.id]` with an `m-*` id against a table keyed `leg_press`.** `kb` is therefore always `undefined` for every real machine; `buildGuide` gets no `setupCues`, `regionOf` falls back to name regexes, `baselineLoad` falls back to the catalog or `50/50`. The README's promise that the Leg Press's eleven setup cues are finally shown here (`SetupGuide.tsx:8-11`) is not kept, and the guide a first-time set-up opens shows warnings and key cues but no set-up steps — the `universalBaseline` seat/pad/gap lines are never read by `buildGuide` at all. `features/catalog/adapters.ts:35-51` does the id translation correctly; this file forgot it. No test passes an `m-*` id through `toEquipmentMachines` (the render test uses `"leg-press"`). Direction: build the guide from `ResolvedMachine.universalBaseline` + `alignmentCheckpoints`; delete the database lookup.

7. **High — `src/features/admin/machines/StudioMachineEditor.tsx:78-81, 117, 137-138` — the resolved machine's bookkeeping is saved as overrides / inside the definition.** `value = resolved` is a `ResolvedMachine` (not passed through `definitionOf`), so `draft` carries `machineId, studioId, source, rosterStatus, order, comparisonKey, overriddenFields, catalogStatus`. For a CUSTOM machine `definition: draft` stores all of them inside `roster.definition`; for an ADMIN editing a studio's copy (`StudioEquipmentPanel.tsx:279` passes `scope="admin"`, and `scopeOverrides` filters nothing for admin) `pruneOverrides` keeps every one as a "difference from the standard" and the toast reads "Solon differs from the standard on name, machineId, studioId, source, rosterStatus, order, catalogStatus, comparisonKey and overriddenFields" **[probe]**. The render test passes a plain definition as `resolved`, so it cannot catch it. Direction: `definitionOf(resolved)` on the way in, and `pruneOverrides` restricted to `keyof MachineDefinition`.

8. **High — `src/features/equipment/SettingsCard.tsx:169-170` (and `MachineSheet.tsx:241-255`) — a settings change cannot be saved without a typed reason, mid-session.** `canSave = dirty && (!needsReason || reason.trim().length > 0)`; the MachineSheet is the in-session sheet. Same pattern in `EditRoutineDrawer.tsx:442, 833` (routine save blocked under 3 characters, labelled "mandatory reason explaining this clinical adjustment") and `ClientProfileView.tsx:625, 1492` (turning Routine B on needs a reason). CLAUDE.md: "Never block a save"; the-floor.md: trainers stopped recording when changing a setting was hard. Direction: the reason is optional and journalled when given; the change itself is the audit record.

9. **High — `src/hooks/useMachineCatalog.ts:42-44` → `useStudioMachines.ts:124, 196-206` → `WorkoutTrackerView.tsx:2090-2097` — `byId` is rebuilt on every render, so the tracker's grid rows are recomputed on every keystroke.** `useMachineCatalog` builds `byId` outside `useMemo`; `useStudioMachines`' memo lists `catalogById` as a dependency, so `machines` and `byId` are new objects every render; the tracker's `gridRows` memo depends on `studioFloorById` and re-runs `toJourneyRows` over every loaded log each time a rep digit is typed in the Now Bar. FileMaker was hated for being "slower with every machine and every session on screen". Direction: memoise `byId` in `useMachineCatalog`, and give the machine list a context so the profile's five separate `machines` listeners (EquipmentTab, MachineSheet, SetupPromptDialog, ClientMachineWindow, SetupView + ClientProfileView) become one.

10. **High — `src/features/catalog/StudioSetupCard.tsx:116-127` + `src/hooks/useStudioMachineSettings.ts` — the "Studio standards, set by your studio leader. Read these to preset the machine" card writes a collection nothing on the floor reads.** Writes `studioMachineSettings/{s}_{m}`; the only readers are the card's two mounts (Catalog page `CatalogWikiView.tsx:672`, My Studio door `MachinesSection.tsx:371`). The tracker, Now Bar, Equipment tab and Setup never read it. The hook's own comment (`:13-16`) claims the Journey grid and Active Session read it for order — no longer true. ARCHITECTURE §3.5 lists this collection as legacy with 0 documents; My Studio (Sep 19) mounted a second door to it. A write with no reader, in the house's own words. Direction: the door's "standard settings" is the roster entry's `overrides.defaultSettings`, already editable in "Set up for us"; delete the card and the hook.

11. **High — `src/types.ts:1763` `Studio.machineSettings` — six readers, zero writers.** Every "studio standard" fallback chain starts with `activeStudio?.machineSettings?.[id]` (`ClientProfileView.tsx:942`, `WorkoutChartGrid.tsx:563`, `PerformanceEntryDialog.tsx:185`, `useFitFloor.ts:40`, `equipment/adapters.ts:386`, `MachineSettingsDashboardModal.tsx:52`) and nothing in `src/`, `server/` or `scripts/` writes it. The first branch of six precedence chains is dead. Direction: delete the field and the branches; the resolver is the one precedence.

12. **High — `neverToFailure` never reaches a trainer on the floor.** The round doc says it is "structured so the session UI can enforce it rather than display it"; its only readers are `MachineEditor.tsx:152-213`, `CatalogList.tsx:244`, `StudioInventoryManager.tsx:542`, `sections.tsx:554-566`, `completeness.ts:207` (grep). The Now Bar, the grid, the briefing and the MachineSheet header have no marker for Lumbar and Cervical; the text survives only as a `clinicalWarnings` line inside a collapsed "Setup guide" (`MachineDetailPanel.tsx:157` opens it only when `!machine.inUse`). Direction: a fixed marker on the Now Bar and the briefing row for the two machines, read from the resolved machine.

13. **High — `src/components/WorkoutChartGrid.tsx:233-244` — a third writer of `clientMachineSettings.settings` with a different contract.** Bare `setDoc(..., {merge: true})`, `updatedBy: email`, no `sources`, no `settingHistory`, no journal, no fit-index upsert; and `merge: true` is the exact trap `equipment/mutations.ts:190-193` documents (a cleared dial comes back). Still reachable: `ClientProfileView.tsx:1665` mounts the chart, which mounts `MachineSettingsDashboardModal` (`:688`). Direction: route it through `equipment/mutations.saveSettings` or remove the modal from the chart.

14. **Medium — two definitions of the shared vocabulary.** `src/types/machines.ts:30-31` says `data/machine-anatomy-map.ts` "re-exports from here so there is exactly one definition". It does not: `machine-anatomy-map.ts:12-34, 299-310` declares its own `AnatomyView`, `MuscleId`, `MovementPattern` and `MOVEMENT_PATTERN_ORDER`, and six files import `MuscleId` from the map while eight import it from `types/machines`. They agree today by coincidence. Direction: make the map import the types.

15. **Medium — the routine engine reads static tables, not the catalog.** `routine-builder/engine.ts:15-16, 88` and `academy.ts:62-200` key anatomy, category, family and abbreviations on the twenty `m-*` ids. Editing a catalog machine's `primaryMuscles`, `sequencingContraindications` or `movementPattern` in the editor changes no rule; a custom or adopted machine is `unmapped` and no sequencing rule can fire on it because `basedOn` is never consulted. ## 4. Direct, challenging questions for AJ

**One model or six**
1. There is one merge policy (`resolve-machine.ts`) and one editor, but the floor reads the legacy `Machine` shape and four static tables instead. Are you willing to make the tracker and the profile read `useStudioMachines` FIRST — before any more machine authoring — and accept that until then everything in `Set up for us`, custom machines and the catalog's dials is invisible to a trainer?
2. `machine-database.ts` (the cue lists), `machine-anatomy-map.ts` and `default-machines.ts` are all inputs to the generator and all still read at runtime. Once `machine-definitions.ts` is seeded, which of the three is allowed to keep existing, and which screen justifies it?
3. `routine-builder/academy.ts` hard-codes muscles, families, categories and abbreviations per id. Is the routine builder's doctrine part of the METHOD the catalog owns (so an admin edit in the editor should change a sequencing rule), or a second, code-owned method that only a developer changes?

**Settings as a labelled list**
4. The editor already lets a studio add any dial by label (`Add a dial`), and every dial is free text — so the model is a labelled list. The floor, though, keys everything by first letter and forces "Gap". FileMaker's chart uses `S, G, B, Pads, H, E, Ft, Blocks` per machine. Do you want the Now Bar to show the unit's own labels (as many as it has) or a fixed `G · B · S · H` strip? Those are different screens.
5. Should "Gap" be a dial like any other, with the Academy's default (2 on the row, per-client on the leg press) as a ghost — or is "Gap 0 for everyone" a real house rule that the catalog's `defaultSettings` are wrong about?
6. FileMaker values are `N / W / M / SH / 1.5`. Do you want per-dial options (a tap picker of `N · M · W` for handles) on the floor, or is a free text box with the keyboard acceptable at the machine?

**Where the notes live**
7. A maintenance flag ("seat sticks") is stored on one client's `clientMachineSettings.machineNotes` and only that client's next briefing sees it. Should machine condition be a studio fact on `studios/{s}/machineNotes` (Relay's machine-care already exists) with nothing per client?

**The Academy and the catalog page**
8. The Academy is code-split correctly and costs the floor nothing until opened — but `machine-definitions.ts` ships to every trainer on every load for one admin button. Is the Academy inside the iPad app because trainers read it on the floor, or because it was the only place to put it? If the latter, Learning could be a separate web page and the machine article stays.
9. Catalog names are your studio's shorthand in caps (`BICEP`, `LUMBAR`, `CX (4 WAY NECK)`) and every other layer spells them differently and joins by name. Do you want the Academy's names as the standard and the floor's names as the studio's `shortName`, or is the shorthand the standard?

**Machine fit, pre-beta**
10. Machine fit is a second suggestion engine (cohort ladder, clusters, k=5 cells) reachable only from Programming → Setup; the floor gets a different, simpler engine (`suggestFromTrend`). With four studios and cells that need five clients, what is the concrete moment a trainer opens Setup in a week — and if it is "when a FileMaker chart is copied", is Quick entry + shorthand the feature and the cohort engine a distraction until the data exists?
11. Should the FIRST-time set-up on the floor (the SetupPromptDialog) show the Academy's baseline lines (seat P2, shoulder pads snug, feet hip-width) — which the definitions carry and nothing on the floor renders — instead of a height-band statistic?

**Blocking**
12. Three saves in this area refuse without a typed reason (settings change, routine edit, Routine B on). Is "reason required" a rule you want, given the-floor.md says trainers stopped recording when the app got between them, and given every one of these changes is already stamped with who and when?
