# The lean Mindbody sync — Sep 25 2026

Branch `lean-sync`, cut from live master (`48560b0`), restore point `restore/2026-09-25-before-lean-sync` (pushed). **Nothing here is on `master`.** It changes the Mindbody integration and the webhook Cloud Function, with AJ's OK (Sep 25: "lets go with your recommendation"), and adds one field to the studio document with its permission. Ship it with `scripts/ship/ship-lean-sync.ps1`.

## Why

The Screen Atlas's cost review (Sep 25) found that Mindbody calls are about nine tenths of what Journey will cost to run. Every studio with an iPad open pulled a whole month of its Mindbody schedule every fifteen minutes, and looked every client in it up again, with nothing kept between pulls. That was about 600 calls a studio a day. A studio on the shared site (westlake, Strongsville and Willoughby, site 29068) downloaded all three studios' bookings every time.

AJ's brief: get that price way down, without trainers missing a cancellation or a change, and keep Refresh so a trainer can always be sure. He chose the recommended path. First the lean pull, then the webhook fixed and switched on over it.

### What the review of phase 1 caught, and how it was fixed

- **A move read as a cancellation.** When a booking for tomorrow moved to later in the week, the two-day pull no longer saw it, and swept it as cancelled until the next month pull. Now a near pull that loses a booking cancels nothing. It asks for the month straight away (`SyncOptions.settleSweepWith`), and that pull files the booking as moved, with its stamps, or cancels it. The Operations overhaul's rule still stands: a swept booking that comes back is a fresh booking.
- **A move into the next two days lost its history.** A booking moved into today or tomorrow from later was written as new, replacing its row. Rows for answer ids the window query did not find are now read by id first.
- **The month pull could be skipped for a block.** The deciding fact is now `Studio.lastDeepScheduleSyncAt`: when the last month pull whose answer was whole was claimed. It is written only after success and is best-effort. If the permission is not deployed yet, the next pull simply reaches the month again, and nothing counts as a failure.
- **A parked booking lost its client's name.** On the shared site the server now skips lookups only for this studio's own bookings. A booking parked for an admin also falls back to Journey's name.
- **Placeholder names counted as real.** Records named "Mindbody" / "Client {id}" and webhook stubs are no longer treated as named.
- **Fewer lookups.** Only the day's first month pull looks every client up; the others skip known clients.

### What the review of phases 2 and 3 caught, and how it was fixed

- **Two events for one booking at once could leave a cancelled session on the Hub.** The webhook now reads the row, checks it and writes it in ONE transaction.
- **A cancellation that arrived first could be lost.** When Journey did not hold the booking yet, the cancellation was simply dropped, and a late created event then put the session on the Hub. Now it leaves a note in `mindbodyBookingCancels/{siteId}-{appointmentId}`, a new collection written by the webhook only. The booking's own event reads that note and lands cancelled. A newer "booked again" event still wins.
- **A trainer could be matched from the wrong site.** Mindbody numbers staff per site, like clients, so a match now counts only for a trainer who works at the booking's studio: the pull's rule. The row also keeps `mindbodyStaffId`, so an unmatched update never clears a trainer the pull found for the same person.
- **The one-studio fallback was too broad.** It now applies only when that studio has claimed no location of its own. Otherwise the pull would filter the booking out and sweep it.
- **A failed health-record write could lose an event, or dead-letter one that had been applied.** It can no longer decide an event's fate.
- **Missing times, other sites and Limbo noise:**
  - An event with no readable time never blanks a booking's time.
  - A booking with no readable time is parked for an admin rather than written without a day.
  - A booking whose id another site's studio holds is parked, never taken over.
  - On the shared site, a client update now reaches Limbo only when the client has no home studio yet.
- **An empty two-day answer hides a cancellation.** A near pull whose answer is empty but whose window still holds a live booking now hands it to the month too.
- **The month was recorded as read when it wasn't.** A month pull whose results failed to save no longer records the month as read.
- **A warning backed off the whole pull.** Only a pull that did not get the whole answer into Journey counts as failed now. Before, a lasting warning (an unmapped location) backed the fifteen-minute pull off to every four hours.
- **The ship script could deploy outdated code.** Turning the webhook on now refuses unless the project folder is exactly what's live on GitHub. It also stops if an old subscription could not be deleted.

## What trainers see

- **Today and tomorrow:** a cancellation, a new booking or a new time shows within about 8 minutes, and at worst about 17, exactly as before, while an iPad at the studio has Journey open. Once the webhook is on, it shows in seconds.
- **Later days:** within about four hours in open hours (the month pulls), at once by webhook, or at once on Refresh.
- **Refresh:** always pulls today through next week straight from Mindbody. It now costs a page or two instead of about seven calls, plus a month pull when a booking left the week since the last one. It then re-reads the week on the iPad that pressed it.

## Known limits (written down, not hidden)

- **An empty answer never cancels anything by itself.** A month pull whose answer is empty stops, because an empty answer can be a glitch and must never cancel a month. A near pull whose empty window still holds a live booking hands it to the month, like any other loss.
- **A name changed in Mindbody** reaches a booking by the next morning's first month pull. It is sooner through the webhook's `client.updated`, or a Master Sync on the profile.
- **Mindbody's webhook times are documented as UTC with a `Z`,** and the webhook reads them that way. No real event has ever reached Journey, so the first one is the test. `webhooks-test` in the ship script tells AJ exactly what to look for.
- **One Limbo entry per event, not per booking** (from before this round): a parked booking's later updates each add an entry, and a cancellation does not reach a parked one. Releasing the newest entry is right; say so to whoever clears Limbo.
- **Appointment ids across the two sites** have never been shown to collide (client ids do). Both the pull and the webhook now refuse to treat another site's row as this booking's; the full fix would be site-qualified schedule ids, which is a larger change.
- **The shared-site location filter is not used.** Whether Mindbody honours `LocationIds` on staff appointments is still unknown; `scripts/probe-mindbody-location-filter.ts` would tell. Using it would cut the shared site's month pull from about 8 pages to about 3. It must stay site-wide on at least one pull a day, because the Limbo queue is the only way a new location is ever seen.
