## What was built

### The first screen: sign-in and boot (boot group)

- **R4 — the boot opens on the trainer record.** The record is read from the iPad's cache first (`getDocFromCache`); with nothing cached the server lookup runs as before. Studios, trainers and networks are read together in one `Promise.all`, and each list carries **unknown, cache or server** (`src/features/front-door/boot-lookup.ts`). A cached list counts only once this iPad has had the server's whole answer for it (`journey_list_seen_<list>`), and a cached trainers list of one record never counts, so a first sign-in never says "1 on the team". The picker says Checking you in, never "No studios yet" or "Not on a studio's team yet" off a list that has not answered; a studio is dropped as missing only on the server's word. The self-watch takes the server's copy when role, active, home or any studio list changes; a record the server says is gone is looked up again quietly. The role claim's read is capped at 2 s, and a claim known to disagree waits up to 10 s. The Kaizen Roster's whole-array writes now read the server's roster first (`useKaizenRoster`).
- **R14 — Auth without the popup helper on a signed-in open.** `src/firebase.ts` calls `initializeAuth`; a device flag (`journey_signed_in_here`, `src/lib/auth-boot.ts`) installs the helper at start only when nobody was signed in here last time. The sign-in screen warms it, and on Safari the buttons wait for it (at most 6 s, "Getting sign-in ready" after 400 ms; `front-door/sign-in-ready.ts`). **Not walked on a device**: Google and Microsoft sign-in must be walked in a Safari tab and the Home Screen app (Round 58).
- **R5 — preconnects** to Firestore, identitytoolkit and securetoken in `index.html`; the helper's two origins only when a sign-in is likely.
- **R15 — a first frame before the script:** the logo's three squares on the front door's dark ground, inline in `index.html`, and a slow line after 6 s on the opening screen.
- **R16 (the boot's listeners)** — the bell reads the newest 100 notices (no `isActive` filter: older notices have none) and the newest 50 notifications plus the unread ones (`readAt == null`, the badge says 100+ when capped); a failed read keeps what was there and says so, never "All caught up". `MindbodyHealthProvider` lives only on Operations → Mindbody, keyed on the person, so it no longer dies at a sign-out. One shared machines listener (`src/lib/machines-store.ts`) instead of two; a failed read is dropped and the next screen reopens it.
- **R30 (code half) — the boot report.** Three marks (auth ready, trainer ready, the Hub's data) and, on a cold open, ONE small report through the error reporter (`src/features/boot-timing/`, `src/lib/client-error-report.ts`): `type: 'boot'` in Render's logs, with standalone or tab and the user agent. This is how the iPad numbers below will finally be measured.

### The Hub (hub group)

- **R6a — `useAutoSync` stores its verdict only when it changes.** It still looks every minute and pulls exactly when it did; `useAutoSync.schedule.render.test.tsx` pins two simulated hours of looks, pulls and reasons, and it passed on the old hook before the change. Renders over those two hours: 122 before, under 25 after.
- **R6 — the Hub works from its own week** (`hub-schedule/hub-window.ts`: yesterday to a week on, stretched to a picked day). The day's moments are worked out again only when the clock passes a booking boundary, or the data or the day change; the directory rows once per studio day, from completed sessions only (`src/lib/completed-sessions.ts`); the strip's dots through a cheap `celebratesOn`. Calendar browsing no longer slows the Hub.
- **R8 — Critical triangles arrive with the cards:** the read takes the bookings' own client ids, and one late-cancel marks listener covers the Hub's window instead of one per day tap.
- **R7 — memoised cards and grid** (`HubCard.sameCard`), a clients `Map`, stable callbacks, and a memoised toast value (a toast no longer redraws its 81 readers).
- **R16 (`useSessions`)** — the 24-hour window moves at the studio's midnight; `sessionsKnown` means the server answered (labels only; no Start, Finish or resume path reads it); unchanged sessions keep their objects. Until the server answers, a finished session the iPad holds still says Done with the right number, and a gap waits rather than saying Not logged.

### The live session (session group)

- **R9 — Start, Discard, Back to Hub, the machine Save and Finish never wait on the network.** Start makes its ids on the iPad and issues ONE batch (the session, the routine only when one is needed, the seed sets) without waiting; the client fields and the arrival note are separate writes, never awaited, so one refused field never rolls back a session. A refused Start is said; since the final review a late refusal keeps the sets typed and takes back only the untouched prefills. A **known gate** stops a second empty Routine A (an empty list from the cache is not "none") and holds the prefill, never Start or Finish; the seed never writes over a weight already typed. Discard is one batch (it no longer touches the legacy `sessionNotes`, which only an administrator may delete and which stopped a trainer's Discard halfway). Back to Hub issues both notes and goes. Finish's "finished elsewhere?" read starts when the End dialog opens, and the tap also checks the live sessions stream. The machine menu's Save and Undo close at once: online, "saved" now means saved on this iPad, and the strip says "saved on this iPad" if no answer comes within 3 s.
- **R10 — the session screen stops redrawing itself.** The Now Bar and the send line keep their own one-second clocks; `useMachineCatalog`'s `byId` is memoised (a new map every render was rebuilding the floor and every grid row on every screen that used it); a keystroke redraws only the row typed in.
- **R11 — the Wrap-up's To-file tray and the session's note sheet** filter the journal stream the tracker already holds, and fall back to their own read when that stream is absent, failed, or the index-less fallback at its limit.

### The profile and the leaders' screens (leader group)

- **R12 — the profile's history is read once per client:** a page's set reads go out together; the page is read again only when one of the client's In-Progress sessions finishes or is discarded (on any iPad), when the Activity Archive's list changes, or on every return if the In-Progress listener failed. A session deleted in the Archive leaves the grid.
- **R26 — Outcomes always includes the studio on screen** (past 25 studios it could vanish). Operations keeps a studio's closed days for 15 minutes and reads today live; sessions that were open when kept are read again by id on every use, and an answer only the cache gave is never kept. "All my studios" on Hours reads a studio's month only when it is opened.
- **R27 — the night's month tally.** Step 6 of the nightly renewals job (`server/month-tally-step.ts`, pure half `src/features/admin/month-tally/`) writes `studios/{s}/watch/hours-YYYY-MM` and `sessions-YYYY-MM` for this month and the four before it, closed days only, naming the sessions it saw open. Hours and Insights read those, today live, and the open ones again by id, and fall back to the raw read; Insights' 1,500-session cut no longer applies on that path. "All my studios" shows a dash, never a zero it didn't count. **Rules change:** those documents are readable by the studio's leaders only, written by nobody from the app. The outcomes summary is deferred (below).

### Firestore indexes and the guard (indexes group)

- **R1, R2, R24 — 39 new composite indexes** (54 → 93, all two- or three-field entries in `indexes`, none in `fieldOverrides`): the eight on the session and profile path, the Hub, Relay, the webhook, sharing and the leaders' screens, the weekly trends job's `exerciseLogs (createdAt, machineId)` (which makes its 90-day read a range instead of all history), two shapes Query Insights showed on Oct 5 that the audit missed (`clients (homeStudioId, renewal.situation)`, `sessions (createdAt, status)`), and the bell's unread query (added at the merge).
- **R3 — no query ships without its index.** `src/lib/firestore-indexes.test.ts` over `src/lib/firestore-index-guard.ts` reads every query in `src`, `server.ts`, `server/` and `functions/src` and fails when one has no index of its scope; a branching query needs one for every branch; constraints it can't follow fail as unreadable; the failure prints the JSON to add. About twenty code comments that said a single-field query "needs no index" were rewritten.

### Cloud Functions (functions group)

- **R23 — `recalcTrainerWindows`** reads only completed sessions of the last 90 days, ordered by `createdAt` descending on the existing `(status, createdAt DESC)` index, streamed and projected to seven fields; 512 MiB and 540 s.
- **R25 — the webhook's claim.** The idempotency record is now a claim with a 2-minute expiry, marked done only after the work commits, so a platform kill at the 10 s timeout no longer loses an event: Mindbody's resend 15 minutes later takes over the claim. After four attempts that all died, the next resend is dead-lettered to `mindbodyDLQ`. `system/health` is written at most once a minute per instance on success; event-log documents carry `studioId` (an established client's home studio on the shared site); staff photos write the trainer only when the photo changed (those functions are exported but not deployed). **`onBookingReminderWrite` and `sendDailySummary` are deleted**: nothing set their flags, and the worker that would read their queue is parked. The two collections' `expiresAt` gets a TTL policy (AJ's gcloud step). No region moves: the webhook URL and the browser's callables stay in us-central1.

### The server and Render (server group)

- **R19 — a deploy lets running requests finish:** `server/shutdown.ts` drains on SIGTERM (keep-alive 120 s, headers 121 s, a 110 s fallback); `render.yaml` gains `numInstances: 1` and `maxShutdownDelaySeconds: 120`, and the web service starts Node itself (`node build/server.cjs`, exactly what `npm start` ran) so the signal reaches it.
- **R18 (code half) — a missing file is a 404 nobody caches** (`no-store`), never the app's page under a script's or an image's address; this has to be live before edge caching is switched on.
- **The error-report door** (`server/log-error.ts`): 120 reports a minute per address, 1,200 overall, a 16 KB body, long stacks trimmed. The boot report passes whole.
- **R20 (the cap, not the plan change) — one chart scan request at a time** for the whole process, checked before the body is read and before the per-person limit, answering busy at once; the importer waits a busy page out for up to 3 minutes ("Waiting for another scan to finish…") and keeps every page already read (`src/services/chart-scan.ts`).
- **R22 (the timeouts) —** each Mindbody attempt gets 30 s (the schedule pull's 500-booking pages 60 s), each Gemini attempt 90 s with 120 s for the whole request, and the sign-in check's Firestore reads 15 s. A timeout is "unknown", never empty or signed out.
- **R33 —** no stable id of the same Gemini model exists (Oct 5 2026), so `gemini-3-flash-preview` stays, with a comment; Google's replacement is a different model and needs its own round with real chart pages.

### The bundle (R13, after the merge)

A leaf module so the Hub's directory row no longer pulls the codex Story; `vendor-ui` narrowed to the pinned utilities; **each screen's stylesheet comes with the screen** (`main.tsx` loads `index.css` and the six token files only; `css-imports.test.ts` walks both doors to My Studio's machines, and found fourteen admin components that drew with `admin.css` without importing it); the toasts, the bottom bar and the Hub move with CSS instead of `motion`; the warm-up waits for idle moments and warms the client profile too; the Functions SDK, the access request and Create client load when used; the first screen's code is one file. **A size budget:** `scripts/check-bundle-budget.mjs` (`npm run check:bundle`, a CI step) fails over 480 KB gzip, when charts, drag-and-drop or motion is on the first screen, or when the build used React's development files; `src/first-screen.test.ts` fails, printing the import chain, if the first screen reaches any of thirteen heavy modules.

Two visible changes come with it: the bottom bar's underline fades in under the tab instead of sliding between tabs, and leaving the Hub no longer waits for its fade.

## The R20 gate (the $18 a month cut)

The web instance drops from `1c-2g` ($25) to `0.5c-512mb` ($7) only when **all four** hold, as written beside the plan in `render.yaml`:

1. Edge caching is on and a second GET of an `/assets/*.js` file answers `cf-cache-status: HIT`.
2. The one-scan-at-a-time cap is live (this round).
3. **Two recorded 14-day windows in a row** (Render Pro keeps metrics 14 days: screenshot Metrics → Memory and CPU before each ages out), each with a deploy and an evening of chart imports, show memory p95 under 300 MB and CPU under 70% in the deploy window.
4. AJ approves the bill change.

Then `plan: 0.5c-512mb` and `startCommand: node --max-old-space-size=320 build/server.cjs` — the heap cap in the start command, never in `NODE_OPTIONS` (that would cap `vite build` too). Back to `1c-2g` on a memory p95 over 300 MB or any out-of-memory or health restart.

## How to ship

`scripts/ship/ship-speed.ps1` (prepare, then golive). **To undo the app:** push the restore tag to master (`git push --force origin restore/2026-10-05-before-speed:master`, ask Claude first). **To undo the functions:** from a checkout of the restore tag, `npx firebase deploy --only functions:mindbodyWebhook,functions:recalcTrainerWindows --project prod`; the two deleted functions come back only with `--only functions:onBookingReminderWrite,functions:sendDailySummary` from the same checkout, which nothing needs. **To undo the rules:** deploy `firestore.rules` from the restore tag. The indexes need no undo: an extra index never breaks a query.
