The lead offered "a short fix round for the Wrap-up stutter (about one more hour of build and lab time)". AJ, Oct 6 2026: **"i love every recommendation you give so lets do it"**.

What the release A/B had found (`harness/perf-lab`, Chrome slowed to iPad classes against the local emulators, 3 reps a build):

1. **The Wrap-up after Finish** (the session alone): the Wrap-up phase's long tasks went 60 → 581 ms on the iPad 10th gen profile and 228 → 1,247 ms on the older iPad; the session's worst interaction 128 → 288 and 192 → 424 ms. A profiled rep put 1.9 s of that phase's 3.9 s of CPU in Firestore and its network channel, and 18 ms in `WrapUpScreen`.
2. **Opening a profile** before the roster migration: the A/B's guess was that the profile waits for the server to confirm a client's totals document is missing (`useMachineTotals` keeps "loading" on an empty cache answer, by design), about 3 s behind the emulator's queue on every open.
3. **The lab:** two client reps timed out with the peek open and one session rep never switched day (a tap before the peek or the day header settled); the 45 s Now Bar wait was too short for a build from before the speed round; and the old-iPad profile re-downloaded everything on relaunch from about 17:00.

## What the cause turned out to be

**The Wrap-up's stutter in the lab is the emulator, not the app, and it came with the speed round, not the release.**

- **The emulator re-sends every listening query whole after every write.** It resets each query and sends every document in it again; production sends only the documents that changed. After Finish that is about 3,500 documents and 8 MB in 40 s: the 300-client roster (4 MB) once Finish writes `clients/{id}`, the client's sessions on two listeners, the studio's day of sessions four or five times, the last fifty sessions' sets six times. Decoded traces show the same data arriving on both builds: `c20d2abe` 3,671 documents / 8.3 MB, the release 3,439 / 7.8 MB.
- **The bisect** (iPad 10 class, the session alone, the Wrap-up phase with a 10 s tail): `c20d2abe` 54 ms (1 good rep; 2 timed out at the Now Bar) and 375 ms in a traced rep; the speed round alone (`7aca6195`) 651, 654, 663 ms; the release 473–797 ms over six reps. So the rise came with the speed round, which was already live. The iPad round and the roster split add one 3 KB totals document to what arrives.
- **Why the speed-round builds pay more for the same data:** the emulator now hands it over in about 540 frames instead of about 31, and the Firestore SDK's CPU in the 30 s after the Wrap-up appears went 1,390 → 2,475 ms, mostly in its sorted document maps. Total CPU was about the same (5,098 vs 5,232 ms), and **the app's own CPU there fell, 282 → 142 ms**. Inside the release's 722 ms of Wrap-up long tasks the app's code is about 10 ms.
- **The original 60 → 581 was partly where the window ends.** The lab's Wrap-up window (`lt.wrapUp`) stops at the database's answer to Finish. On `c20d2abe` the roster's re-send landed just after that answer, outside the window; on the release just before it, inside. `PERF_LAB_WRAPUP_TAIL_MS` now keeps measuring past the answer when two builds are compared.
- **Suspects cleared:** the `useMachineTotals` listener (one 3 KB document, read once), Finish's two-document batch (the roster re-send happens on `c20d2abe` too), the listeners re-attached after Finish (the same set on both builds).
- **One real app regression, small, found and fixed:** `withMachineTotals` built a new object for the client on screen every time AppContent rebuilt its client list, which it does on every roster change, other clients' included. The session, the Wrap-up behind it and the profile then redrew for somebody else's change, undoing for that one client what the iPad round's roster work won for all of them (`docs/KNOWN-TRAPS.md`, "a fold must hand back the same object").
- **The worst interaction, 128 → 288 ms, is not the Wrap-up.** It is the briefing's Start session tap (320–330 ms), because since the speed round the Now Bar is drawn inside that tap instead of after the database's answer: Briefing → Now Bar went 484 → 217 ms while that one tap grew. A speed-round trade-off, left alone.

**Opening a profile never waited for the totals.** `ClientProfileView` never reads the totals' state, and the Journey grid's loading is the sessions read alone. The A/B's explanation (waiting for the server to say the totals document is missing) was wrong. Six opens in a row in the lab: the release 813 ms, then 3,870, 3,743, 3,444, 3,306, 3,421 ms; `c20d2abe` 794, then 1,252–3,427. The cause is the emulator's queue: the previous profile's five parallel `exerciseLogs` `in` reads (the speed round's R12) keep it busy about 4.5 s, and every new listener waits behind them. Production answers reads as they come.

## What is estimated, not measured

- **A real iPad's Wrap-up should stutter far less than the lab's, on both builds.** Production does not re-send whole queries after a write, and the re-send is most of the lab's Wrap-up phase. That is reasoning from how the emulator and production differ, not a number from an iPad; Round 59 is where it gets one.
- **The app's share of the Wrap-up's work is about 75–90 ms on the iPad 10 class and 150–200 ms on the older iPad**, of 2.2–3.1 s of CPU in that phase (single profiled reps). No change to the app can bring the lab's number under 150 ms; that target was not met and can't be in this lab.
- **The fix is at most a modest gain**: it stops redraws caused by another client's change, which is a real but small part of what happens after Finish. In the profiled reps the app's share did not fall.

## How to ship

**Superseded (Oct 7 2026):** master moved on to `27484683` (Running low, Talk now, Slipping away) before this shipped, and the renewals dashboard was built on this branch merged onto it (`40385a83`). The Wrap-up fix therefore goes live with `scripts/ship/ship-renewals-dashboard.ps1` (`docs/rounds/2026-10-07-renewals-dashboard.md`, "Deploy order"); `ship-wrapup.ps1` would refuse, and is kept only as the record of what was planned.

```powershell
cd C:\Users\austi\Projects\Journey-System-Beta-master\.claude\worktrees\wrapup
powershell -ExecutionPolicy Bypass -File .\scripts\ship\ship-wrapup.ps1 -Stage prepare
powershell -ExecutionPolicy Bypass -File .\scripts\ship\ship-wrapup.ps1 -Stage golive
```

`prepare` checks everything and changes nothing; `golive` tags `restore/2026-10-07-before-wrapup` at master, deploys the rules only if they changed (they don't), stops if any Cloud Function changed (none did), and pushes. **A push deploys nothing on Render** (found Oct 6 2026), so golive then prints the three buttons: Manual Deploy on the web service, Manual Build on `journey-cron-renewals` and `journey-cron-leaderboards` (both carry the changed file; nothing they compute changes). Then the iPads back on the Hub once, and Round 59's Wrap-up round lines. To undo: push the restore tag to master and press the same three buttons.

**Master must be exactly `40b868a2`.** If anything else has gone to master since, prepare stops: the branch has to take it in and be measured again first.
