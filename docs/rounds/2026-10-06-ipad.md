## What AJ asked

AJ, Oct 5 2026: **"we really need our app to run fast on devices like ipads even 10th generation ipads and ipad minis"**. ## The lab (`harness/perf-lab/`)

**What it is.** The real app, built the real way, run in headless Chrome slowed down to iPad classes, against local Firebase emulators holding one big seeded studio, through the scenarios a trainer and a leader actually live in. Its `README.md` is the manual; the short version:

- **A seeded studio:** Lakeside, 300 clients, 6 trainers, the twenty machines, 8 weeks of bookings, 26 weeks of sessions (about 12,000), exercise logs for the last 4 weeks (and two focus clients with a year each), about 600 notes, FORD, announcements, and the nightly record (renewal snapshots, client states, All stars) worked out by the nightly job's own pure code. About 35,600 documents. Its clock is held at 09:40 Eastern on the day it runs, so a run at 2 AM sees the same mid-morning Hub as one at 3 PM.
- **Profiles:** iPad 10th gen (820 × 1180 at 2×, JavaScript 3× slower than the reference), iPad mini (744 × 1133, 3×), an older A12/A13 iPad (1180 × 820 landscape, 5×), desktop (1×), and `floor` (1×, no added network: what is left with the iPad taken away). The slowdown is **calibrated** to the PC running it before every rep (the reference is AJ's PC on Oct 6 2026, 235 ms on the lab's benchmark), because Chrome's throttle is not the number you give it. Every iPad profile adds 60 ms of latency (gym Wi-Fi to Oregon), touch, and iPad Safari's user agent.
- **Scenarios:** a cold first sign-in, a warm reload, a **relaunch** (the headline: a Home Screen app that iOS put away), the first open after a deploy, the Hub left idle 70 s, a client's profile from the Hub, a whole session (Start, the briefing, five sets, the machine menu, Finish, the Wrap-up), Operations → Today and the Directory, scrolling, and (opt-in) `live`: one client document changing while the Directory or the Hub is open.
- **It never touches production.** Emulators only, under the project `demo-perf-lab`, on Firestore **8085** and Auth **9099** (so the rules tests on 8080 can run beside it). Every script refuses unless both emulator hosts are on 127.0.0.1, the project is `demo-*` and no credential is set. **A lab build can't ship:** `vite.config.ts` refuses `VITE_PERF_LAB=1` into `dist/` or on Render, a lab build carries `PERF-LAB-BUILD.txt`, and `server/served-files.ts` refuses to serve a folder that has it; `src/perf-lab-hook.test.ts` and `src/services/served-files.test.ts` hold it, and `ship-ipad.ps1` checks the production build for the lab's markers.

**How to run it** (PowerShell, from the project or a worktree; Node 22+, Java, Chrome; nothing on 8085 or 9099):

```powershell
node harness/perf-lab/lab.mjs all                                   # everything, about an hour
node harness/perf-lab/lab.mjs all --profiles ipad10-portrait --reps 1 --idleMs 10000 --no-profile-rep
node harness/perf-lab/lab.mjs build --as before                     # on the old code
node harness/perf-lab/lab.mjs build --as after                      # on the new code
node harness/perf-lab/lab.mjs run --build-a before --build-b after  # A/B, alternating rep by rep
```

Results go to `%TEMP%\journey-perf-lab\<run-id>\` (`report.md`, `results.json`, screenshots). Only one lab may run on the PC at a time: the ports are shared.

**What it can't tell.**

- **Safari's paint and compositing.** Chrome (V8 and Blink) slowed down is not WebKit on an A14 or A12. The calibration matches JavaScript speed on one benchmark; backdrop blur, shadows, sticky layers, opacity layers and hatching (the paint group's work) are WebKit GPU and raster costs the lab does not model. Safari Web Inspector → Timelines → Rendering Frames, on a real iPad connected to a Mac, is the final word for those.
- **Real devices and real Wi-Fi.** Every number is a calibrated estimate of a device class, not a device. The real numbers come from the speed round's boot report (`type: 'boot'` in Render's logs) and AJ's timed walk (Round 59).
- **The emulator's own waiting.** Finish's 5 s (the app's two Finish waits running out against a slow emulator) and Start → briefing's 4 s on every profile, desktop included, are the emulator's: a trace on the floor group's branch found the emulator holds each new listener's request until it has worked out its queries, which production does not.
- **Scale.** Only 300 clients were seeded; production rosters go to 1,500. Roster-driven costs grow with it; that run has not been made.

## What was built

### The app stops redoing work (CPU group, `oct6/ipad-cpu`)

- **Studio time without asking Intl every call** (`abcfa81e`, `src/lib/studio-time.ts`). The zone's offset is read three times per UTC day (its first second, noon, its last second) and remembered per zone and day; the rest is arithmetic. A day whose readings differ holds a clock change and still reads every instant from Intl exactly as before. New `formatDateWords`: `toLocaleDateString`'s words from a formatter built once. `studio-time.cache.test.ts` compares every answer with the old Intl reading: every minute across both 2026 clock-change nights, the edges of days, Lord Howe's half hours, 4,000 instants over six years in ten zones.
- **A day in words without a new formatter per row** (`06bb4302`, `3bf453c1`): Operations' per-client sentences, Journey, Month, cases, moments, the next days, the Hub card's day markers, the live session's day, the renewal engine and sentences, Changes and the Week pages.
- **One client's change rebuilds one client** (`c227aef5`, `src/lib/studio-roster.ts` `rosterFromSnapshot`): `useStudioRoster` converts only the documents that changed; every other client stays the same object, and a snapshot that changed nothing hands back the same list.
- **The Directory redraws one row, not all 300** (`52697aee`): a row cache, a memoised row, stable callbacks from `AppContent`.
- **The minute passing no longer redraws the Directory** (`965a6b93`, `src/lib/boundary-clock.ts`): the clock still looks every minute but hands out a new time only when the studio's day turns or a booking edge passes (half an hour before, start, end, end plus the slack: `bookingBoundaries` in `lib/booking-state.ts`, the instants every booking state changes at).
- **Operations stops working everything out again every minute** (`2e0b9e89`): Journey, Month, Trends, Team, the Week pages and a client's page on the boundary clock; Today keeps its minute for the light parts and keys its heavy models on `useSettledNow`.
- **Every client's journey in a tenth of the time** (`74eea46e`): `shiftIndex` reads today's bookings once instead of once per client.
- **Shared iPads don't grow memories for ever** (`45480e88`, W11): Load older keeps the last 8 clients, the closed-days keep lets go 15 minutes after its last use, the calendar's FORD the last 6 ranges.
- **The Hub's day rebuilds one client's row on a change** (`b9ecf955`).

### What WebKit paints (paint group, `oct6/ipad-paint`)

- **No blur behind dialogs, sheets, toasts and sticky bars** (`0bf4572d`, W3): 17 uses removed; the navy scrim a little stronger to make up for it (light .30 → .36, dark .55 → .60); toasts solid; the Deep Dive's bar opaque. `src/paint-cost.test.ts` fails on any blur.
- **A card among many takes one short shadow** (`beb96fe7`, W7): a new `--elev-list` (one navy layer, 0 1px 3px) on fifteen kinds of repeated card; the soft lift stays on a panel there is one of, and on dialogs and popovers. `elevation.test.ts` section 15 holds it.
- **Marks that beat three times, then rest** (`b9f5299a`, W10): the Session tab's dot, the Hub's live dot, the profile's In progress clock and the Kaizen ring; the intro banner is still; Operations' skeleton sweep moves a band instead of repainting.
- **A lighter Hub card** (`2c8dc65e`, W12): the column is the container, not each card; finished cards fade with a veil of the ground instead of an opacity layer; the off-hours hatching is a small tile. A harness of 4,806 cards at every column width found the glyph words appear at exactly the same widths as before.

## The roster split (a separate step: AJ's OK to the structure change)

Built on `oct6/ipad-data` (with `oct6/ipad` merged in). **Not part of `ship-ipad.ps1`.** CLAUDE.md: "Don't change ... the Firestore structure without an explicit OK."

**What moves.** Three fields leave every client document, `clients/{id}`: `currentMachineMetrics` (the last set on each machine: Start's prefilled weights, the grid, the briefing, the machine menu; about 6.8 KB), `machineStats` (each machine's lifetime rollup: first and last weight and day, times performed; about 3.4 KB) and `machineStatsBackfilledAt` (the backfill's marker). They go to ONE document per client, `clients/{id}/machineTotals/current`, beside the client like `inbodyScans`. Nothing else moves (`lifetimeReps`, the renewal snapshot, the Mindbody fields stay).

**Why.** Every open of the app streams the studio's whole client list, and 73% of each client document was these two maps, which the Hub, the Directory and Operations' lists never draw. The client document drops from about 14 KB to about 3.8 KB: a 300-client studio's roster from about 4.15 MB to about 1.15 MB per open (about 72% less), and at the 1,500-client limit from about 20.7 MB to about 5.7 MB. The iPad's offline cache of the roster shrinks the same way.

**What it buys, in seconds (estimated from the lab's measured sizes, not from an A/B run):** the Firestore SDK and stream decoding took about 5 s of an older iPad's open and grow with the bytes taken in: roughly **3 s saved on an older iPad and 2 s on an iPad 10th gen or mini** per morning open. The same branch also gives the Hub's day a **head start**: the roster listener waits until the Hub's day has answered (or 3 s), only on the Hub, online, so the Hub's day should land about **1.5–2 s from the open on an iPad 10th gen instead of about 6.6 s** (the trainer record arrives at about 1.1 s; the day's own read follows it). Every later client change is also a smaller message to decode.

**How it stays correct.** One merge rule (`src/features/machine-totals/totals.ts`, `mergeMachineTotals`) is used by every reader and by the migration: per machine, the later last set wins; times performed is the SUM of the two sides, which holds because no write ever copies a count across without deleting it in the same write. So a client reads the same before, during and after the migration, and an iPad still on the old version (writing the old fields) is counted correctly. A totals document still loading is "unknown", never "nothing on file": Start's prefilled weights wait for it as they wait for the machine settings; Finish with the totals unknown writes the counts and today's last set only; "Finish it as it was" and Log past session's Save say "Reading the machines…" for that moment. The rules refuse SETTING `machineStatsBackfilledAt` on a client (an old iPad's backfill would otherwise double the counts). The nightly and weekly jobs read the totals documents by id (`getAll`), no query and no new index. No Cloud Function reads or writes these fields. `src/features/machine-totals/README.md` is the whole design.

**The migration.** `scripts/split-client-metrics.ts` moves the fields, client by client, 20 to a transaction: it writes the merge into the totals document, deletes the three fields from the client, and moves `lastSessionDate` forward to the last machine day where that is later (the Directory's "Last in" read it from the maps). Dry run by default; `--commit` writes; `--studio <id>` one studio; `--limit <n>`; refuses a real project unless its id is typed twice. Idempotent and resumable: a moved client is skipped, a failed transaction leaves its clients untouched, and a second run later moves anything an old iPad wrote meanwhile. With `--commit` it writes what every moved client held before to `backups/split-client-metrics-<time>.json` after each transaction.

**The order** (`ship-ipad-roster.ps1`, after `ship-ipad.ps1`): the restore tag; the rules tests, then the rules (they only add the new document's access and refuse the old backfill's marker; the running app is unaffected); then the push (the app writes to the new document and reads both sides; nothing on the roster changes yet); then **AJ runs the migration**, once the iPads have loaded the new version: a dry run, then `--commit` one studio at a time. Only then does the roster shrink. The script prints each command.

**The way back.** Before the migration, nothing needs undoing: the app reads both sides. After it, the app on master reads the new document, so the split itself never needs undoing for the app's sake; only a build from before this round would miss the fields. To run one again, copy the fields back first: `scripts/unsplit-client-metrics.ts` (on the same branch) writes the same merge back onto each client and deletes its totals document in one transaction, dry run by default. The ship script prints the exact order.

**What a list no longer has after the migration** (visible):

- **The Hub on a slow open:** the day's cards can appear a moment before the client marks (the Critical triangle, a total like "#312", renewal and All stars) fill in, because the client list now loads after the day. They show as loading meanwhile, as they did while the roster loaded.
- **Operations → Renewals → a client's brief, "3. Strength":** says "Reading the machine history…" while that client's totals load, or "Couldn't read the machine history. It will try again." if the read fails (it used to say "Not enough machine history in Journey yet." at once).
- **Session Start** for a client whose totals haven't loaded (never opened on that iPad, or offline): the prefilled weights appear a moment after Start, as they already wait for machine settings. Offline with nothing cached, they wait until the iPad is back online.
- **"Finish it as it was" and Log past session's Save** say "Reading the machines…" for that moment.
- **Programming → Setup's suggestions and Operations → Machine fit (this studio)** no longer count a set-up accepted from a suggestion (they read "performed since" from the roster's maps). Fewer samples, never a wrong one; set-ups a trainer typed are unaffected, and the weekly all-studios tier still counts them. **Open for AJ:** keep a small per-machine "last day" map (about 0.6 KB) on the client if the studio tier should count them.
- **The Directory's "Last in"** keeps its day (the migration moves `lastSessionDate` forward).
