# The demo week — Sep 20 2026

**Demo Mode had a year of history and an empty Hub.**

The round after Demo Mode, on the same day. One new file
(`src/features/demo-mode/week.ts`), one new test file, and four small edits.

AJ's brief:

> For our demo mode we need to make a mock hub schedule that has its clients
> scheduled for that week's sessions … it doesn't have to be real, it just has
> to be interactable for demo mode so trainers can feel what it would be like
> to open a client from the hub. We can just have the demo mode replaying the
> same schedule every week so it can just not take up a lot of space.

---

## The gap

Everything the Demo Mode seeder laid down was **history** — 130 sessions, 910
sets, a year of weights that climb the way a real client's climb. The Journey
grid, the profile, Renewals and the Operations Overview all read backwards, so
all of them worked.

The Hub reads **forwards**, out of `schedules`, and the seeder wrote nothing
there. So the first screen a trainer opens in Demo Mode — the one with the
trainer columns and the blocks you tap to start a session — was blank, in a
studio otherwise full of people. The single most common thing a trainer does
in this app was the one thing they could not practise.

## What it is

`DEMO_WEEK` is eleven standing appointments: a weekday, a wall-clock time, a
client and the trainer who takes them.

| Sun | 9:00 | Merry Brandybuck | Aragorn |
| Mon | 9:00 | Eowyn Rohan | Aragorn |
| Mon | 9:30 | Rosie Cotton | Pippin |
| Tue | 7:00 | Sam Gamgee | Gimli |
| Tue | 10:00 | Arwen Evenstar | Aragorn |
| Wed | 5:30 PM | Frodo Baggins | Pippin |
| Thu | 9:00 | Eowyn Rohan | Aragorn |
| Thu | 9:30 | Rosie Cotton | Pippin |
| Fri | 7:00 | Sam Gamgee | Gimli |
| Fri | 10:00 | Arwen Evenstar | Aragorn |
| Sat | 8:00 | Frodo Baggins | Pippin |

Clients train twice a week, so every standing pair is three or four days apart
— Mon/Thu, Tue/Fri, Wed/Sat — the way a package is actually booked. The
retired clients have the mornings and the two who work have 7 AM and the
evening, which is the shape of a real Max Strength floor. Two columns run at
once on Monday and Thursday, so the grid has something to be a grid about.

**Merry is the exception, deliberately.** He has been away forty-three days —
that is what he is in the roster to teach — so he has no standing pair, just
one Sunday make-up with the studio leader. The attendance anomaly and the
booking that answers it, on the same screen.

The pattern is laid down again for **eight weeks** from the day the seeder
runs: 88 documents, seven per cent on top of the seed, and two months before
anybody has to press Reset.

## The three decisions worth writing down

### 1. The ids count occurrences; they never name a day

The seeder has no wipe, on purpose (`seed-write.ts`). So every id it writes has
to be an id it will write *again* next time — otherwise a reset in October
leaves September's bookings behind with nobody to delete them, and the demo
studio slowly fills with ghosts.

`demo-booking-eowyn-2026-09-21` is exactly that mistake. A booking is instead
identified by **which of that client's upcoming appointments it is** —
`demo-booking-eowyn-003` — and the run always holds the same number of them,
because any 56-day window contains exactly eight of every weekday whatever day
it starts on. Every reset rewrites the same 88 ids with new dates. A test
proves it by building the run from seven consecutive start days and comparing
the id lists.

### 2. Nothing is laid down in the past

`renewals/attendance.ts` reads a past booking that was not cancelled as a
**visit**. A seeder that filled in last week to make the Hub look busy would be
quietly telling the renewals engine that Rosie came in when she did not — and
Rosie is the client the whole renewal demo hangs on. So the run starts today,
and the history that already exists is what the past is made of.

### 3. The wall clock, not a UTC hour

The session history sidesteps timezones by only ever using UTC hours 13–21,
which are the same Eastern calendar day all year (`instantOn` in
`seed-core.ts`). Bookings cannot take that shortcut: a 7 AM standing
appointment has to read as 7 AM in November as well as in September, and an
hour of seasonal drift on a standing appointment is the kind of small wrongness
a trainer notices at once. `wallClockToInstant` resolves the offset for the
actual date, and a test builds a run that crosses the change to standard time
and asserts Sam is still at seven on both sides of it.

## Two things it got for free

**Every day of the week carries at least one booking, Sunday included.** That
is the one place the pattern is arranged for the demo rather than for realism.
The Hub opens on *today*; a trainer who opens Demo Mode on a Sunday to an empty
grid does not conclude that the studio is closed, they conclude the demo is
broken — which is the exact impression this round exists to prevent.

**One booking in the run is cancelled** — the last one on the first day from
today + 2 that has any. Operations → Overview → Changes is otherwise
permanently empty inside Demo Mode, and it is the panel a studio leader opens
on a Monday to find exactly this. It lands on a client who holds another
booking that week, so `changesForDay` reads it as a **reschedule** and the row
says where it moved to — the more useful of the two readings, and the one that
needs a second booking to demonstrate at all.

## What a block needs to be tappable

The Hub resolves a block **strictly**: `clients/{clientId}` or nothing, never a
name match (hub sync fixes, Sep 16). A booking whose `clientId` is not a seeded
client document draws as "Not synced" and opens nobody — which is precisely the
interaction AJ asked for, so the test that pins it is the important one.
`trainerName` is matched case-insensitively against `trainer.fullName` to
choose the **column**; a name the Hub cannot place conjures a "virtual" column
instead of using the demo trainer's.

`source` is `"Manual"`, not `"MindBody"`. The demo studio is
`mindbodyMode: "offline"` with no site id, so claiming Mindbody put these here
would be the one lie in the seed that a trainer could catch. `serviceName` is
`"Training Session"`, which `isDefaultService` recognises, so the blocks carry
no service chip — a service name only earns one when it says something the
trainer did not already know.

## No rules change

`schedules` already allows create and update for any authenticated trainer,
subject to `isValidSchedule` — `clientName`, `trainerName`, `startTime`,
`endTime`, `status`, `serviceName`, `source`. A test asserts all seven are on
every booking, because a missing one is a write refused halfway through a
batch, in front of the boss.

**`firestore.rules` and `firestore.indexes.json` are untouched by this round.**
The Demo Mode round's rules and indexes still have to deploy first; this adds
nothing to that list.

## The one thing that expires

Everything else in Demo Mode is history and stays true forever. The schedule
runs out. So the card on the studio selection screen now says how many bookings
went in and **what date they run through**, and that setting it up again moves
the schedule forward. A date rather than a surprise.

`DEMO_SEED_VERSION` is **3**.
